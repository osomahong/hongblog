# prose-inspector

hongblog 콘텐츠의 문체 검수 스킬. **문어체 검출과 낭독 검수를 분리해 둘 다 강제한다.**

## 이 스킬이 존재하는 이유

2026-08, SEO 코스 9강을 쓰면서 `scripts/check-prose.ts`가 HARD 0건으로 통과하는 것을 문체 검증으로 착각했다.
그 스크립트는 정규식 20여 개만 본다. `갈래`, `얹히다`, `비로소`, `정본` 같은 문어체는 목록에 없어서
**통과 신호가 나와도 문체는 전혀 검증되지 않은 상태였다.** 배포 후 사용자가 지적해 전량 재수정했다.

그래서 이 스킬의 원칙은 하나다. **기계 통과는 검수의 시작이지 끝이 아니다.**

## 3단계 절차

세 단계를 모두 통과해야 커밋할 수 있다. 하나라도 건너뛰지 않는다.

### 1단계. 번역투와 금지 기호 (기존 게이트)

```bash
npm run check:prose -- <파일 경로>
```

HARD 0건이어야 한다. 이 단계는 em dash, 가운뎃점, `~에 대한`, `~을 통해`, 이중 피동 등을 본다.

**오탐이 나올 수 있다.** 실제로 있었던 사례다.

| 검출 | 실제 | 처리 |
|---|---|---|
| `목록 첫 페이지에 있어` | 존재의 `있다` | 문장을 바꿔 우회 |
| `noindex 태그에 의해 제외됨` | 서치 콘솔 실제 UI 문구 | `allowContext` 예외 추가 |

오탐이면 우회하거나 예외를 등록하고, **왜 오탐인지 사용자에게 보고한다.** 조용히 넘기지 않는다.

### 2단계. 문어체와 추상 표현 (이 스킬)

```bash
node ${CLAUDE_SKILL_DIR}/scripts/check-literary.mjs <파일 경로>
```

HARD 0건이어야 한다. WARN은 맥락에 따라 허용되므로 3단계에서 판단한다.

사전 항목과 근거는 `references/literary-lexicon.md`에 있다.

### 3단계. 낭독 검수 (기계가 못 하는 층위)

본문을 처음부터 끝까지 읽으며 아래 일곱 가지를 본다. **grep으로 대신할 수 없다.**

| 항목 | 무엇을 보는가 | 실제로 나왔던 예 |
|---|---|---|
| 주어와 서술어 호응 | 주어가 그 동사를 할 수 있는가 | `세 동사가 순서대로 일어난다` → `세 단계가` |
| 주어 누락 | 무엇이 하는 일인지 적혔는가 | `상품이 많은 사이트에서 자주 나옵니다` → `이 상황은 상품이 많은` |
| 목적어 누락 | 무엇과 무엇을 하는가 | `낯선 개념은 비유로 연결합니다` → `비유를 먼저 두고 설명합니다` |
| 비유 성립 | 비유의 원재료가 만질 수 있는 사물인가 | 허용: 요리, 집, 일상 사물, 교통 |
| 비유 중복 | 같은 비유를 두 번 쓰지 않았는가 | 강별 비유는 미리 배분한다 |
| 표와 도표 안 문장 | 본문과 같은 규칙을 지켰는가 | 마크다운 표, 인라인 HTML 도표에서 반말 의문형이 세 번 샜다 |
| 인접 문장 종결 | 같은 어미가 붙어 나오지 않는가 | `~않습니다` 두 문장 연속 |

**표와 HTML 도표를 빠뜨리지 않는다.** 이 세 곳이 실제로 가장 많이 샜다.

### 3-1. 지칭과 명명 (2026-08 사용자 교정)

기계로 일부만 잡힌다. 나머지는 읽으면서 본다.

| 항목 | 규칙 | 잘못된 예 → 고친 예 |
|---|---|---|
| 자기 지칭 | 이 사이트의 클래스는 **강의가 아니라 교육 목적 콘텐츠**다. `강의`, `이번 강`, `6강`으로 부르지 않는다 | `이번 강의 주제입니다` → `이 글에서 다룹니다` |
| 상호 참조 | 번호로 부르지 않고 **개념 이름**으로 부른다 | `6강, 7강에서 다시 나옵니다` → `정규 URL과 내부 링크를 다룰 때 다시 나옵니다` |
| 대명사 | `자기`, `그것`, `이것`으로 넘기지 않고 **주체 이름**을 적는다 | `자기가 아는 주소만` → `크롤러 봇이 알고 있는 주소만` |
| 비유 헤딩 | 비유만 단독으로 쓰지 않고 **원개념을 함께** 적는다 | `골목을 도는 우편배달부` → `크롤러봇, 배송을 담당하는 배송기사` |
| 개념 헤딩 | 비유에서 쓴 말을 개념 설명 헤딩에 전용하지 않는다 | `크롤러가 도착하지 못하는` → `크롤러가 웹사이트를 색인하지 못하는` |
| 조어 | 사전에 없는 조합을 만들지 않는다 | `세대 명단` → `등록된 주소록` |

### 3-2. 의미 불명 압축 (2026-08 사용자 교정)

**읽고 뜻이 바로 안 잡히면 그 문장은 실패다.** 수식 관계가 모호한 명사구가 원인인 경우가 많다.

| 잘못된 예 | 문제 | 고친 예 |
|---|---|---|
| 링크가 얕은 페이지를 보완합니다 | `링크가 얕은`이 무엇을 수식하는지 모름 | 링크를 적게 받는 페이지의 발견을 돕습니다 |
| 시작 전에 알아 둘 제약은 | 무엇에 관한 제약인지 없음 | 구글 옴니를 쓸 때 알아둬야 할 제한적인 점은 |

판정 방법은 하나다. **그 문장만 떼어 소리 내어 읽었을 때 뜻이 한 번에 잡히는가.**
두 번 읽어야 하면 고친다.

### 3-3. 근거 표현 (2026-08 사용자 교정)

| 항목 | 규칙 | 예 |
|---|---|---|
| 문서명 | 정확한 제목을 모르면 단정하지 않는다 | `크롤링 예산 문서에서` → `크롤링 관련 문서에서` |
| 근거 신호 | 공식 근거를 댈 때 신호어를 붙여 인용임을 드러낸다 | `구글도 ~라고 설명합니다` → `실제로 구글도 ~라고 설명합니다` |

## 사전 확장 (핵심)

사용자가 새 표현을 문어체나 비문이라고 지적하면 **그 자리에서 사전에 등록한다.**
등록하지 않으면 다음 글에서 같은 표현이 다시 나온다. 이 스킬을 만든 이유가 이것이다.

```bash
node ${CLAUDE_SKILL_DIR}/scripts/check-literary.mjs --all
```

등록 절차는 세 단계다.

1. `scripts/check-literary.mjs`의 `RULES`에 항목을 추가한다. `src`에 지적 시점과 출처를 남긴다
2. `references/literary-lexicon.md`에 대체안과 사용자 지적 맥락을 적는다
3. `--all`로 기존 콘텐츠 전체를 훑어 같은 표현이 남아 있는지 확인한다

**추측으로 항목을 넣지 않는다.** 사용자 교정 이력, `writing-style-guide.md`, 메모리 규칙에서 근거가 확인된 것만 넣는다.
근거 없는 항목을 넣으면 오탐이 늘어 스킬 전체가 무시된다.

## 판정 기준

WARN 항목과 사전에 없는 표현은 이 질문으로 판단한다.

> 이 표현을 평범한 사람이 동료에게 말할 때 자연스러운가, 아니면 신문 사설이나 논문 같은가?

후자면 바꾼다. 판단이 서지 않으면 사용자에게 묻는다.

## 출력 형식

파일을 직접 고치지 않는다. 아래 형태로 보고하고 승인을 받는다.

```
## 문체 검수: <파일명>

| 단계 | 결과 |
|---|---|
| check:prose | HARD 0건 / SOFT 0건 |
| check-literary | HARD 2건 / WARN 1건 |
| 낭독 검수 | 비문 3건 |

### 수정 제안
| # | 위치 | 현재 | 제안 | 근거 |
|---|---|---|---|---|
| 1 | L41 | 모르는 데서 옵니다 | 몰라서 생깁니다 | 번역투 |
```

승인 후 Edit으로 적용하고, **적용 뒤 1~3단계를 다시 돌린다.** 수정하면서 새 위반이 생기는 일이 실제로 있었다.

## 하지 않는 일

- SEO, AEO, GEO 점검: `inspect-content` 스킬이 담당한다
- 제목 추천: `seo-title-creator` 스킬이 담당한다
- 사실관계 검증과 출처 확인: 이 스킬의 범위가 아니다. 다만 근거 없는 단정형을 발견하면 보고는 한다
- 파일 자동 수정: 승인 없이 고치지 않는다
