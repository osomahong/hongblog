# 작성 기법 (쓰는 방법)

`prose-rules.md`가 하지 말 것을 정한다면 이 문서는 할 것을 정한다. **3단계 작성에서만 읽는다.** 검수 단계에서는 읽지 않는다.

기준 표본은 osoma.kr 블로그 5편이다. 쿠키리스 시대 전략, UTM 가이드, GA4 유입경로 탐색, 제3자 쿠키 폐지, 크로스 도메인 추적. 아래 예문은 전부 그 글에서 가져왔다.

## 1. 중심 비유

### 하나만 세우고 끝까지 끌고 간다

낯선 개념을 설명하는 글에는 **중심 비유를 하나** 정한다. 도입에서 세우고 본론에서 항목별로 갈아 끼운다. 한 번 쓰고 버리지 않는다.

UTM 글이 택배 송장으로 글 전체를 끌고 간 방식이다.

```
도입   UTM을 쉽게 설명하자면 택배 송장이라고 할 수 있습니다.
본론1  송장만 보고도 누가 보냈는지, 어디서 온 택배인지, 내용물은 무엇인지
       알 수 있듯 → utm_source, utm_medium, utm_campaign
본론2  택배를 받으면 내용물을 확인하고 정리하는 것처럼 → 데이터 정합성
```

곁가지 비유는 한 번씩만 쓴다. 중심 비유는 글당 하나다. 두 개를 세우면 읽는 사람이 어느 축으로 이해해야 할지 놓친다.

### 대조가 필요하면 축을 둘로 나눈다

무엇이 무엇으로 바뀌는지 설명할 때는 비유 하나에 양쪽 항을 붙인다. 제3자 쿠키 글이 우편과 이메일로 잡은 방식이다.

```
과거   우편 서비스는 실제 주소를 사용하여 특정 개인에게 직접 편지를 보냅니다.
       수신자가 아니더라도 편지를 배달하는 과정에서 우체부를 비롯한 어떤 사람들은
       수신자의 주소와 개인정보를 낱낱이 확인할 수 있는 것처럼
현재   이메일은 실제 우리가 살고 있는 주소 대신 온라인상의 이메일 주소를 사용하며,
       보내는 사람과 받는 사람 사이의 통신이 비교적 안전하고 개인적인 방식으로 이루어집니다.
```

이건 비유 두 개가 아니라 **한 축의 양 끝**이다. 중심 비유 하나로 센다.

### 원재료 고르기

만질 수 있는 사물이어야 한다. 아래 계열에서 고른다.

| 계열 | 재료 |
|---|---|
| 우편, 배송 | 송장, 겉봉투, 우체부, 주소 |
| 요리, 주방 | 부엌, 레시피, 재료, 창고 |
| 집, 건물 | 방, 문패, 안방, 현관 |
| 일상 사물 | 상자, 서랍, 서류함 |
| 교통, 도로 | 길, 번지수, 표지판 |
| 상점 | 서점, 카페, 진열대 |

판별 질문 하나로 정한다. **이 비유의 원재료를 손으로 만질 수 있는지 본다.**

### 하지 말 것

| 잘못 | 이유 | 고침 |
|---|---|---|
| 쿠키가 없는 웹사이트는 알츠하이머에 걸린 것처럼 | 질병을 비유 재료로 쓰면 읽는 사람이 다치고, 만질 수 있는 사물도 아니다 | 쿠키가 없는 웹사이트는 방문자를 매번 처음 보는 사람으로 대합니다 |
| 시스템의 그림을 그리지 못합니다 | 비유가 아니라 관용구를 흉내 낸 빈 표현 | 시스템의 구조를 이해하기 어렵습니다 |
| 빌린 것이 이자로 돌아온다 | 원관념과 보조관념이 어긋난다 | 빌려 쓴 시간에 이자가 붙는다 |

## 2. 문장과 어휘

### 비유는 종속절로 붙인다

비유를 따로 떼어 설명하지 않는다. `~듯`, `~처럼`으로 본문 문장 안에 접합한다. 이 방식이 osoma 글이 친절하게 읽히는 실제 문법이다.

```
송장만 보고도 누가 보냈는지, 어디서 온 택배인지, 내용물은 무엇인지 등
송장만 보고도 쉽게 알 수 있듯 (...)

택배를 받으면 내용물을 확인하고 정리하는 것처럼 (...)

과거에는 우편 서비스를 통해 편지를 주고받았듯, 디지털 광고 업계는
사용자의 온라인 활동을 추적하는 제 3자 쿠키에 기록하는 방식에 크게 의존했습니다.
```

앞절이 비유, 뒷절이 원래 이야기다. 순서를 바꾸지 않는다.

### 용어는 `즉`으로 그 자리에서 푼다

영어 용어나 공식 명칭을 쓰면 같은 문장 안에서 바로 한국어로 옮긴다. 다음 문단으로 넘기지 않는다.

```
유입경로 보고서는 Funnel exploration 즉, 퍼널 분석(탐색) 보고서이며
사용자 프라이버시, 즉 개인정보 보호를 강화하는 동시에
```

첫 등장에는 한국어를 앞에, 영어를 괄호에 넣는다. `쿠키리스(Cookieless)`, `검색 엔진 최적화(Search Engine Optimization)`. 두 번째부터는 한쪽만 쓴다.

### 사실 앞에 크기를 체감시키는 부사를 놓는다

`무려`, `바로`, `절대로`를 숫자나 결론 앞에 놓는다. 금지된 과장(`혁명적`, `획기적`)과 다르다. 그 표현들은 사실 없이 감탄만 하지만, 이쪽은 뒤에 검증 가능한 사실이 붙는다.

```
쿠키는 무려 1994년에 인터넷 익스플로러보다 오래된 최초의 브라우저인 넷스케이프에서
무려 전 세계 웹사이트의 80% 이상이 사용하는 구글 애널리틱스는
구글 애널리틱스는 바로, 이 Urchin이라는 회사에서 만들었습니다.
이번 변화는 절대로 디지털 마케팅의 종말을 의미하지 않습니다.
```

한 글에 세 번을 넘기지 않는다. 뒤에 사실이 없으면 쓰지 않는다.

### 읽는 사람의 걱정을 적고 곧바로 뒤집는다

감정을 연출하는 것과 다르다. 지금 어떤 상태인지 서술하고, 다음 문장에서 판단을 준다.

```
구글의 이번 조치가 마케팅 업계에 타격을 주지 않을까 많은 디지털 마케터 분들의
걱정이 많은 상황입니다. (...) 마케터들 사이에서 불안한 이슈로 이야기되는 것도
당연하지만 이번 변화는 절대로 디지털 마케팅의 종말을 의미하지 않습니다.
```

한 글에 한 번, 도입부에만 쓴다. 본론에서 반복하면 연출이 된다.

### 단정을 한 단계 낮추는 종결

판단을 담은 문장은 `~라고 할 수 있습니다`, `~라고 볼 수 있습니다`로 닫는다. 공식 문서로 확인한 사실만 `~입니다`로 쓴다.

```
GA4에서 가장 매력적인 기능을 꼽으라고 한다면 바로 이 유입경로 탐색 분석이라고
할 수 있습니다.

Urchin은 GA의 전신이라고 볼 수 있는 서비스의 이름입니다.
```

### 문단은 `이처럼`, `이런`으로 이어 받는다

앞 문단의 내용을 지시어로 받아 다음 문단을 연다. 접속부사(`그래서`, `그러나`)를 문단 첫머리에 두는 것보다 흐름이 매끄럽다.

```
이처럼 도메인이 분리된 환경에서는 사용자의 여정을 (...)
이런 구조에서는 사용자의 여정을 하나의 흐름으로 (...)
이런 문제를 해결하기 위해 Montulli는 (...)
```

지시어가 가리키는 대상이 바로 앞 문단에서 하나로 정해져야 한다.

### 다음으로 무엇을 할지 화자가 예고한다

읽는 사람에게 행동을 시키지 않고, 글쓴이가 자기 행동을 알린다.

```
서점에서 책을 찾는 과정을 예로 들어 생각해보겠습니다.
이 글에서는 구글 Privacy Sandbox가 어떤 변화를 준비하는지, 그리고 마케터들이
어떻게 이 변화를 받아들여야 하는지에 대해 설명하려고 합니다.
```

`상상해 보세요`, `떠올리면서 읽어 주세요`는 금지된 AI식 지시문이다. 차이는 주어다. 주어가 글쓴이면 쓰고, 읽는 사람이면 쓰지 않는다.

### osoma에서 가져오지 않는 것

| 항목 | osoma | hongblog |
|---|---|---|
| 문장 길이 | 쉼표로 길게 잇는다 | 쉼표 3개를 넘으면 쪼갠다 |
| 자사 언급 | `저희 오픈소스마케팅은` | 1인칭 수집 표현과 자사 언급 금지 |
| 마무리 | 문의 유도 | 3줄 요약 |

2인칭 `여러분`은 osoma와 같이 쓴다. hongblog 49편 가운데 10편이 쓰고 있고 `독자`의 정식 대체 호칭이다. 금지되는 것은 `독자`와 `당신`이다.

문장 길이가 특히 어긋난다. osoma의 도입부 두 번째 문장은 쉼표 다섯 개에 90자가 넘는다. 문장 길이를 따라가지 말고, **정보 밀도만 가져오고 문장은 끊는다.**

```
그대로 옮기면
  쿠키는 무려 1994년에 인터넷 익스플로러보다 오래된 최초의 브라우저인
  넷스케이프에서 낮은 성능의 웹페이지 메모리 문제를 해결하기 위해 발명되었습니다.

끊어 쓰면
  쿠키는 1994년 넷스케이프에서 나왔습니다. 인터넷 익스플로러보다 앞선
  최초의 브라우저입니다. 당시 웹페이지의 낮은 메모리 성능을 해결하려고 만들었습니다.
```

## 3. 개념 도입 순서

### 기원을 먼저 말하고 정의를 나중에 준다

용어를 던지고 뜻을 붙이는 대신, 어디서 왔는지부터 푼다. 읽는 사람이 개념을 낯선 말이 아니라 사연이 있는 물건으로 받는다.

```
쿠키는 무려 1994년에 인터넷 익스플로러보다 오래된 최초의 브라우저인 넷스케이프에서
낮은 성능의 웹페이지 메모리 문제를 해결하기 위해 발명되었습니다. (...)
이런 문제를 해결하기 위해 Montulli는 웹사이트가 방문자를 기억할 수 있도록
컴퓨터와 웹사이트 간 전달이 가능한 데이터 조각인 쿠키를 생각해냈습니다.
```

```
UTM이라는 이름은 Urchin Tracking Module의 줄임말이고
Urchin은 GA의 전신이라고 볼 수 있는 서비스의 이름입니다.
```

기원을 못 찾으면 생략한다. 지어내지 않는다.

### 브리지 문구 뒤에 굵은 한 줄 정의를 박는다

정의 문장 앞에 한 마디를 놓아 속도를 늦춘다. 그 뒤에 완결형 정의를 굵게 쓴다.

```
웹사이트 쿠키를 한 줄로 요약하자면 **사용자가 웹사이트에 재방문했을 때 웹사이트를
빠르고 편리하게 사용할 수 있도록 저장한 작은 데이터 조각**입니다.
```

쓸 수 있는 브리지 문구는 `쉽게 설명하자면`, `한 줄로 요약하자면`, `쉽게 말해`, `정리하면` 정도다. 한 글에 세 번을 넘기지 않는다.

이 정의 문장은 metaDescription, 도입부, JSON-LD에서 표현을 맞춘다. 삼중 정렬은 `prose-rules.md` 6절에 있다.

### 정의 문장의 압축 용어는 바로 다음 섹션에서 푼다

도입 정의 문장에 `해싱된 자사 고객 데이터`처럼 전문 개념이 겹쳐 압축된 표현을 썼다면, 도입 직후에 풀이 섹션을 하나 둔다. 표현을 단어 단위로 나눠 불릿으로 풀고, 마지막에 완결형 재정의를 굵게 쓴다.

```
## 해싱된 자사 고객 데이터란 무엇일까요?

첫 문장에 쓴 표현을 먼저 풀고 가겠습니다. 두 단어로 나누면 쉽습니다.
- **자사 고객 데이터**: 고객이 우리 웹사이트에 직접 남긴 정보입니다. (...)
- **해싱(Hashing)**: 원문을 알아볼 수 없는 문자열로 바꾸는 처리입니다. (...)
정리하면 해싱된 자사 고객 데이터는 **고객이 직접 남긴 연락처를, 사람이
알아볼 수 없는 암호 형태의 값으로 바꾼 것**입니다.
```

이 풀이 섹션의 질문형 H2는 핵심 쟁점 자리로 계산한다. 2026-08-12 향상된 전환 글에서 사용자 교정으로 확정했다.

### 낯선 개념에는 브리지 세 줄

전문 개념을 처음 꺼내는 섹션 초입에 넣는다.

1. 낯섦 인정: `~라는 개념은 ~보다 상대적으로 낯설 수 있습니다` (비교 기준을 반드시 붙인다)
2. 완결형 재정의: `쉽게 말하면 ~입니다`
3. 예고: `준이아빠블로그에 실제 적용된 ~를 그대로 보여드리겠습니다`

## 4. 도입부

### 세 박자로 짠다

**읽는 사람이 아는 것 → 모르는 것 → 그래서 생기는 위험** 순서다. 문제 상황만 던지는 것보다 한 단계 깊다.

```
쿠키가 사라진다는 것쯤은 이제 누구나 알고 있습니다.          ← 아는 것
심각한 상황이라는 것도 알고 있지만, 구체적으로 왜 심각한 건지,
어떻게 디지털 마케팅에 위협이 되는지 잘 알지 못합니다.        ← 모르는 것
그만큼 쿠키는 너무나 당연하게 생각되는 기능이라 특별히 관심을
두지 않으면 사라지고 난 뒤 큰 혼란을 겪을 수 있습니다.        ← 그래서 생기는 위험
```

### 개념이 아니라 상황이 주제면 사례로 연다

도구 사용법이나 구축 사례는 세 박자 대신 구체적 장면으로 시작한다. 가상의 도메인과 버튼 이름까지 적는다.

```
때로는 한 서비스 내에서 두 개 이상의 도메인을 거쳐야만 전환이 완료되는 사례가 있습니다.
대표적으로 비영리재단의 후원 시스템처럼, 후원 정보를 제공하는 웹사이트(자사 도메인)와
실제 결제를 진행하는 외부 솔루션(외부 도메인)이 분리된 경우입니다.

예를 들어 후원자가 cocoa.org라는 웹사이트에서 캠페인 내용을 확인 후 '후원하기' 버튼을
클릭하면, cocoa.payments.org와 같은 외부 결제 시스템으로 이동하게 됩니다.
```

### 분량

2~3문단이다. 도입부에서 결론을 미리 말하지 않는다. 3줄 요약은 글 끝에 있다.

## 5. 추상 개념을 표로 보여주기

정의를 두 번 설명하는 대신 **가상 데이터 표**를 깐다. 개념 차이가 눈으로 보인다.

퍼널 글이 폐쇄형과 개방형을 가른 방식이다.

```
1) 행동 패턴 표
   User_A  1단계 → 2단계 → 3단계
   User_B  2단계 → 3단계
   User_C  1단계 → 3단계
   User_D  1단계 → 2단계

2) 같은 데이터를 두 방식으로 집계한 표
   단계     폐쇄형   개방형
   1단계      3        3
   2단계      2        3
   3단계      1        3
```

표 두 개면 문단 다섯 개가 줄어든다. 정의 문장은 표 아래에 한 줄로만 붙인다.

쓸 자리는 이렇다.

- 비슷한 개념 둘의 차이 (폐쇄형과 개방형, 세션과 사용자)
- 설정값에 따라 결과가 달라지는 경우
- 계산 방식이 여럿인 지표

## 6. 정보 계층

| 항목 | 기준 |
|---|---|
| 문단 | 2~4문장. 5문장을 넘으면 쪼갠다 |
| H2 아래 문단 | 3~5개. 2개면 H2를 합치고, 6개를 넘으면 H3로 나눈다 |
| 리스트 전환 | 병렬 항목이 3개 이상이면 문장으로 나열하지 않고 불릿으로 뺀다 |
| 표 | 항목이 2개 축을 가질 때만. 한 축이면 리스트로 충분하다 |
| 이미지 | 실제 화면 스크린샷. 절차 설명 글은 단계마다 한 장을 붙인다 |

절차를 설명하는 글은 이미지 밀도를 높인다. GA4 유입경로 글은 10장을 썼고, 단계마다 어느 메뉴를 누르는지 화면으로 보여준다.

## 7. 글 유형별 골격

### 개념 해설 (쿠키리스, 제3자 쿠키)

```
도입 세 박자
개념의 기원과 한 줄 정의
지금 바뀌는 배경 (이해관계)
바뀐 뒤 달라지는 것 (중심 비유로 대조)
대응 방법 (실행 항목)
자주 묻는 질문 2~3개    ← 질문형 H2
3줄 요약
```

### 도구 사용법 (UTM, GA4 유입경로)

```
도입: 이 도구가 무엇인지 한 줄 + 중심 비유
제대로 써야 하는 이유
구조와 항목 (항목마다 스크린샷)
실전 템플릿 (복사해서 쓸 수 있는 형태)
자주 묻는 질문     ← 질문형 H2
3줄 요약
```

템플릿 절은 그대로 복사해 쓸 수 있어야 한다. 설명 없이 값만 채워진 예시를 놓는다.

### 구축 사례 (크로스 도메인)

```
도입: 구체적 장면 (가상 도메인, 버튼 이름까지)
문제 상황
연결 방법 (설정 절차)
확인할 수 있게 된 것
3줄 요약
```

### 무언가를 만드는 과정 (코덱스로 도구 만들기, 자동화 구축)

AI 도구로 무엇을 만드는 과정을 보여주는 글이다. 만드는 절차만 늘어놓기 쉬운데, **그 절차는 이 글에서 가장 덜 중요한 부분이다.**

```
도입 세 박자 (설치는 쉽다 → 첫 한 줄을 모른다 → 그래서 안 쓰게 된다)
무엇을 만드는지            ← 아래 4항목을 반드시 채운다
시킬 말 (복사 가능한 코드블록 전문 + 터미널 이미지)
실행 명령과 옵션
나온 결과 (화면 + 그래서 무엇을 알게 되었는지)
이어서 고치는 법
자주 묻는 질문 2~3개    ← 질문형 H2
3줄 요약
```

**만드는 대상이 어떤 분야의 개념을 다루면, 그 개념 섹션에 네 가지가 전부 들어가야 한다.**
2026-08-16 코덱스 CLI 글에서 사용자 지적으로 확정했다. 첫 판에는 "AI 검색에
인용되기 좋은 글인지 점검하는 도구"라고만 적고 GEO라는 이름도, 왜 지금 이 주제인지도,
더 깊은 설명으로 가는 링크도 없었다.

| 항목 | 내용 |
|---|---|
| 개념의 이름 | 정식 명칭과 한국어를 병기한다. `GEO(Generative Engine Optimization), 즉 생성형 엔진 최적화` |
| 왜 지금 이 주제인지 | 요즘 이걸 궁금해하는 이유를 한 문단. 검색 유입 감소처럼 읽는 사람이 겪는 변화와 잇는다 |
| 더 깊은 설명 내부 링크 | 개념 클래스 1~2개, 실행 순서나 실측 데이터 글 1~2개. 이 글이 개념 전체를 설명하려 들지 않는다 |
| 왜 이 도구인지 | 원칙은 알아도 확인이 안 되니 자동화한다는 식으로, 개념과 도구를 잇는 한 문단 |

만든 도구가 점수나 판정을 내놓으면 **공식 지표가 아니라는 단서를 결과 절에 붙인다.**

실패했던 시도는 적지 않는다. 다만 **누구나 겪고 대응이 명확한 것 하나**는
실패담이 아니라 방법의 한 줄로 옮긴다. 자기 컴퓨터에만 있는 설정 문제는 뺀다.

### 데이터 검증 (자사 GA4, SEO 성과)

`prose-rules.md` 7절의 유형별 톤을 함께 따른다. 실수치 노출 규칙이 있다.

## 완료 전 자문

작성을 마치고 아래를 스스로 묻는다. 기계가 못 잡는 층위다.

- 중심 비유가 하나이고 두 곳 이상에서 확장되었는지
- 낯선 개념마다 브리지 문장이 붙었는지
- 도입부에 읽는 사람이 아는 것과 모르는 것이 구분되어 있는지
- 개념 차이를 설명한 대목을 표 없이 문장으로만 풀지 않았는지
- 질문형 H2가 FAQ와 핵심 쟁점 자리에만 있는지
- 절차 설명에 화면 이미지가 붙었는지
