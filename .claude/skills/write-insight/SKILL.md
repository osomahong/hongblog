# Insight 포스트 작성 스킬

블로그 Insight 포스트를 **주제 분석 → 웹 리서치 → 콘텐츠 작성 → MD 파일 생성**까지 일괄 수행한다.

## 워크플로우 (6단계)

### 1단계: 주제 분석 & 요구사항 정리

- `$ARGUMENTS`에서 주제, 카테고리, 핵심 포인트를 파악한다.
- 카테고리는 `MARKETING`, `AI_TECH`, `DATA` 중 하나 (Insight 전용).
- 불명확한 사항이 있으면 AskUserQuestion으로 사용자에게 확인한다.
  - 예: 카테고리, 기술 수준, 강조할 포인트 등

### 2단계: 웹 리서치

- WebSearch / WebFetch로 공식 문서, 최신 자료를 조사한다.
- 수집할 것: 기능 목록, 통계 데이터, 실무 사례, 공식 문서 URL
- 검색 시 현재 연도(2026)를 포함해 최신 정보를 우선한다.
- 수집한 Sources URL은 마지막에 본문에 포함한다.

### 3단계: 콘텐츠 작성

**제목·헤딩 규칙 (담백체):**
- 마케팅적 수사, 감탄사, 질문형 제목 금지
- **담백한 서술문** 형태로 작성 — 사실을 그대로 진술하듯 쓴다
- 독자를 자극하거나 호기심을 유발하려는 표현을 쓰지 않는다
- 글 제목(title)과 본문 H2 헤딩 모두 동일한 규칙을 따른다

| 금지 패턴 | 올바른 예시 |
|-----------|-----------|
| ~~"검색 트래픽 25% 증발" — 그 뉴스, 진짜일까요?~~ | AEO/GEO 시대, 검색 트래픽 변화를 데이터로 검증했습니다 |
| ~~마크다운, 들어는 봤는데 뭔가요?~~ | AI시대에 마크다운이 중요한 이유 |
| ~~충격! AI가 검색을 죽이고 있다~~ | AI Overviews 도입 이후 오가닉 CTR은 61% 하락했습니다 |
| ~~당신이 몰랐던 SEO의 비밀 5가지~~ | SEO에서 자주 오해되는 5가지 사실 |

**본문 은유·수사 규칙:**
- 은유는 **일상 대화에서 실제 쓰이는 비유만** 사용. 광고·영화 대사 같은 극적 은유 금지.
- 판단 기준: "이 표현을 평범한 사람이 동료에게 말할 때 자연스러운가?" 아니면 "광고 카피나 영화 나레이션 같은가?"
- **금지 단어 목록**: `변신`, `마법처럼`, `놀랍게도`, `놀라운`, `놀랍도록`, `혁명적`, `획기적`, `차원이 다른`, `상상을 초월하는`, `완전히 새로운`, `세상을 바꾸는`, `기적처럼`, `엄청나게`(강조 부사), `순식간에`(강조 부사)
- **허용되는 은유**: 요리/집/창고/부엌/문패/공장/도로 같은 일상적·구체적 실물에 뿌리 둔 비유는 계속 권장. 구체적이고 사실적이기 때문.

| 금지 표현(본문) | 대체 서술 |
|---------------|----------|
| ~~내 노트북을 웹 서버로 변신시킨다~~ | 내 노트북에서 작은 서버 프로그램이 실행된다 |
| ~~AI가 마법처럼 코드를 짜준다~~ | AI가 코드를 대신 작성한다 |
| ~~놀랍게도 3초 만에 완성됩니다~~ | 3초 만에 완성됩니다 |
| ~~혁명적인 방식으로 데이터를 처리합니다~~ | 기존과 다른 방식으로 데이터를 처리합니다 |

**담백함·근거 수위 규칙 (2026-07 사용자 확정, 모든 글 필수):**
- **제목은 검색 키워드형 명사구**: "~원인과 대응 순서를 정리했습니다" 대신 "~원인과 대응법 정리". 선언형 어미보다 실제 검색어 형태를 우선한다.
- **1인칭 관찰·수집 표현 금지**: "제가 모은", "모아 봤습니다", "바꿔 봤습니다", "추렸습니다" 금지 → "사례들을 바탕으로", "정리했습니다", "정리하면 다음과 같습니다"로 쓴다.
- **근거 수위에 따라 단정 강도 조절**: 공식 문서로 확인된 내용만 단정형("~입니다")으로 쓴다. 커뮤니티·경험담 기반 서술은 완화형으로 쓴다: "구조적으로 생깁니다"→"생길 수 있습니다", "공통점이 뚜렷합니다"→"공통점이 존재합니다", "글이 많은"→"사례들이 있는".
- **연출성 장면 묘사·감정 수식 제거**: "빨간 알림이 떠 있습니다" 같은 장면 연출, "~는 마음으로 정리했습니다" 같은 감정 표현 금지. 상황 설명은 한 문장으로 압축한다.
- **같은 안내를 두 번 하지 않는다**: 앞 문장과 의미가 겹치는 당부·안내 문장은 삭제한다.
- **Sources에는 공식 문서만**: 출처 목록에는 공식 도움말·정책 문서·공신력 있는 기관 자료만 올린다. 커뮤니티 글과 개인 블로그는 본문에서 "~라는 사례가 있습니다"로만 언급하고 출처 목록에 넣지 않는다.
- **highlights는 행동 지침 중심 2개 내외**: 수치·시한 정보는 본문에서 다루고, 요약 카드에는 "무엇을 먼저 하라 / 무엇을 하지 마라" 성격의 항목만 남긴다.

**자연스러운 한국어 문장 규칙 (2026-07 사용자 직접 수정에서 추출, 모든 글 필수):**
- **선언형 강조 마무리 문장 금지**: "이것이 ~의 전부이자 핵심입니다", "~가 정확히 이 지점입니다" 같은 힘주는 마무리를 쓰지 않는다. 설명이 끝나면 그대로 문단을 끝낸다. "~한 이유가 정확히 이 지점입니다" → "~하는 이유가 바로 이런 이유 때문입니다" 또는 문장 삭제.
- **사실 서술도 한 단계 완화**: 예외가 있을 수 있는 서술에는 여지를 남긴다. "수십 분씩 혼자 작업합니다"→"작업하기도 합니다", "표준이고"→"표준 대안이고", "공식 기능으로 들어오고 있습니다"→"공식적인 기능으로 자리잡으려 하고 있습니다".
- **문어투·번역투 동사 회피**: "질문이 나옵니다"→"질문이 떠오릅니다", 기계·프로그램이 주어가 아니면 "돌아갑니다" 대신 "진행됩니다"를 쓴다.
- **읽는 사람을 3인칭으로 지칭하지 않는다**: "사람은 기다리기만 해야 할까요?" 대신 "우리는 기다려야만 할까요?"처럼 글쓴이를 포함한 "우리"로 쓴다.
- **"낯설다" 표현에는 비교 기준을 붙인다**: "cmux라는 이름이 낯설 수 있습니다" 대신 "cmux라는 이름은 tmux보다 상대적으로 낯설 수 있습니다"처럼 무엇에 비해 낯선지 명시한다.

**스타일 규칙:**
- 존댓말 어투 (~습니다/~합니다) 통일
- H2 헤딩(`##`) 최소 3개
- **H2는 가능한 한 질문형(`~을까요/~ㄹ까요/~인가요`)으로 톤을 통일**한다. 명사구 헤딩(`개요`, `결론` 등)은 지양. AEO/FAQPage 스키마 인용 가치를 높이고 사이트 톤 일관성을 유지하기 위함.
  - **예외 (2026-07 사용자 지시): FAQ형 케이스 정리글**은 질문형 대신 "macOS에서 클로드코드 설치 시 발생하는 오류와 해결법"처럼 검색 키워드형 명사구 헤딩을 쓴다. 글 제목도 같은 패턴("~시 발생하는 오류와 해결법 정리")을 따른다. 케이스는 `### "실제 오류 문구"` + 상황/원인/대응법 세트로 구성.
- 본문 최소 1000단어
- 실무 적용 가능한 구체적 예시 최소 1개
- 마지막에 **3줄 요약** 포함
- 마크다운 테이블, 리스트 적극 활용
- **"독자"라는 단어 금지** — 대체 호칭: "이 글을 읽는 분들", "여러분". 자세한 금지 어휘 목록은 `writing-style-guide.md` 참조
- **추상 영어 용어(레이어, 페어, 스택 등) 금지** — "기능", "요소", "Q&A", "쌓인 구조" 등 구체 한국어로 대체
- **병렬 설명 3개 이상은 불릿 리스트로 분리** — 산문 한 문단에 "A는 ~, B는 ~, C는 ~"로 나열되는 구조는 AEO 인용 가치가 떨어진다. `- **용어**: 설명` 형식으로 리스트화

**초보자 친화 브리지 문장 (신설, AEO 인용 가치 강화용):**

전문 개념을 다루는 H2 섹션 초입에 다음 구조의 1~2문장을 삽입한다.

1. **낯섦 인정**: "~라는 개념이 낯설 수 있습니다" / "~용어가 생소하실 수 있습니다"
2. **완결형 재정의 (선택)**: "쉽게 말하면 ~입니다"
3. **예고**: "이 블로그에 실제 적용된 ~를 그대로 보여드리겠습니다"

이 브리지는 음성 검색과 AI Overviews가 그대로 답변으로 가져갈 수 있는 자연어 완결 문장으로 작동한다. 자세한 기준은 `aeo-checklist.md`의 "8. 초보자 친화 안내 브리지 문장" 항목 참조.

**본문 이미지 규칙 (필수):**

본문에는 시각 자료를 최소 1장(권장 2~3장) 포함한다. 이미지는 **추상 일러스트나 자체 생성 그래픽이 아닌, 외부에서 검색한 실제 예시 이미지**여야 한다.

작업 흐름:
1. WebSearch / WebFetch로 주제와 직접 관련된 실제 예시 이미지를 검색한다.
   - 우선순위: ① 공식 발표 페이지(예: `anthropic.com/news/...`, `openai.com/blog/...`) ② 평판 좋은 외신 기사(TechCrunch, The New Stack, VentureBeat, 9to5Mac, Gizmodo, MacRumors 등) ③ 공식 문서
   - 적절한 후보: 실제 인터페이스 화면, 결과물 스크린샷, 공식 다이어그램, 사용량/설정 화면 등
   - **부적절한 후보**: 추상 일러스트, 손/연필 같은 상징 그림, 자체 생성 SVG, 의미 없는 헤더 아트
2. 이미지 URL을 추출한 뒤 `curl -sL -o public/images/insights/{slug}/{descriptive-name}.{ext}` 형식으로 다운로드한다.
   - 외부 핫링크 절대 사용 금지(상대 사이트 도메인이 변하면 깨짐)
   - 폴더가 없으면 `mkdir -p public/images/insights/{slug}` 먼저
3. 마크다운에서 `![구체적 alt 설명](/images/insights/{slug}/{filename})` 형태로 삽입한다.
   - **alt 텍스트는 이미지가 무엇을 보여주는지 한 문장으로 구체적으로** 작성 (스크린리더·검색엔진 인용용)
   - 예: `![클로드 디자인의 주간 사용량 한도 화면, 매주 금요일 오전 8시 리셋](/images/insights/claude-design/claude-design-redesign-example.png)`
4. 위치: 도입부 직후 1장 + 본론 중간 1~2장 권장
5. 본문 단락에서 이미지 출처와 맥락을 명시한다 (예: "아래 이미지는 The New Stack의 분석 화면입니다")

**사용자 피드백:**
- 초안 작성 후 사용자에게 공유하고 피드백을 받는다.
- 피드백 반영 후 최종본을 확정한다.

### 3.5단계: 윤문 검수 게이트 (필수, 생략 불가)

초안이 완성되면 MD 파일 생성 전에 아래 검수를 순서대로 통과해야 한다.
**이 게이트를 통과하지 않은 글은 파일로 만들지 않는다.** 배포 후 반복 수정을 막기 위한 장치다.

**1. 기계 검사 (HARD 0건이 통과 조건):**

```bash
npx tsx scripts/check-prose.ts content/insights/{slug}.md
```

- 금지 기호, 번역투 11종, 과장 표현, AI식 안내 지시문, 반말 의문형 헤딩, 사용자 교정 이력 표현을 자동 검출한다.
- HARD 위반은 해당 문장 전체를 재작성한다 (단어만 치환하면 문장이 어색해진다).
- SOFT 항목(어미 반복, 남용 계열)은 2번 낭독 검수에서 판단한다.

**2. 낭독 검수 (문장 단위, 전체 1회):**

전문을 소리 내어 읽는다고 가정하고 한 문장씩 아래를 점검한다. 하나라도 걸리면 그 문장을 재작성한다.

- **호응**: 주어와 서술어가 맞물리는가. ("~순간이 있습니다"가 앞 절과 붙는가, "시간이 지나도 ~하면 됩니다" 같은 어긋남이 없는가)
- **주어·목적어 누락**: "다행인 점은 눈에 보인다는 것입니다"처럼 무엇이 보이는지 빠진 문장이 없는가.
- **비유의 의미 성립**: "빌린 것이 이자로 돌아온다"(원금·이자 혼동)처럼 비유 자체가 논리적으로 깨진 곳이 없는가.
- **지시어 선행사**: "이 상태", "그 결과"의 지시 대상이 바로 앞 문장에서 명확한가.
- **같은 단어 연속**: 한 문장에 같은 동사 어근 3회("쓰면~쓰더라도~쓰는"), 인접 문장에 같은 종결어("보겠습니다. ~보겠습니다.")가 없는가.
- **처음 언급에 '다시' 금지**: 아직 다루지 않은 내용을 "다시 다루겠습니다"라고 쓰지 않았는가.
- **검증 불가 단정**: "처음으로", "최초로", "가장" 같은 주장을 출처 없이 쓰지 않았는가. (확인 안 되면 "널리 알려진 계기가 된" 수준으로 완화)
- **개념 정확성**: 원문 개념을 요약하며 뜻이 바뀌지 않았는가. (예: 의도 부채는 기록의 존재가 아니라 부재의 문제)

**3. 배포 승인 게이트 (필수):**

- 검수를 통과한 **전문을 사용자에게 먼저 출력**하고 승인을 받는다.
- **승인 전에는 커밋도 배포도 하지 않는다.** "작성해줘"라는 요청은 초안 작성 요청이지 배포 승인이 아니다.
- 사용자가 명시적으로 "배포해줘", "올려줘"라고 한 경우에만 커밋·푸시한다.

### 4단계: MD 파일 생성

- `references/post-schema.md`를 참조하여 MD 파일을 생성한다.
- 파일 경로: `content/insights/{slug}.md`
- **frontmatter 필수 필드:** slug, title, excerpt, category, tags, publishedAt, metaTitle, metaDescription, ogTitle, ogDescription, ogImage, quiz
- 태그는 `src/lib/constants.ts`의 `CANONICAL_TAGS` 목록에서만 선택 (3~5개)
- 퀴즈: 선택지 3~4개, explanation 2~3문장
- slug: 영문 소문자 + 하이픈, 간결하게 (예: `gmail-api-what-you-can-do`)

**썸네일 생성:**
- `/generate-thumbnail` 스킬 또는 `npx tsx scripts/generate-og.ts --slug <slug>`
- `public/og/{slug}.png` 생성 후 frontmatter `ogImage` 필드에 경로 설정

### 5단계: 결과 보고

- 생성된 파일 경로, slug, URL(`/insights/{slug}`) 출력
- 사용자에게 추가 작업 여부를 확인한다 (SEO 점검 등)
