# sns-writer

블로그 글 하나를 쓰레드, 인스타그램, 링크드인 세 벌의 카피로 옮긴다.
**같은 글이라도 플랫폼마다 글은 완전히 달라야 한다.** 길이만 줄인 같은 문장을
여러 곳에 올리면 어느 채널에서도 성과가 나지 않는다. 플랫폼별 차이는
`references/platforms.md`에 정리돼 있고, 문체 규칙은 `references/writing-rules.md`에 있다.
사용자가 특정 플랫폼만 지목하면 그것만 쓴다. 지목이 없으면 세 벌 모두 쓴다.

## 0. 부르는 방법과 대상

**대상 콘텐츠는 세 종류다.** insight(인사이트 글), class(용어 정의), course(코스 개요) 모두 SNS로 옮긴다. 종류마다 소재를 잡는 방식이 달라서 2번 소재 고르기에서 나눠 다룬다.

**명령어 규격.** 텔레그램에서는 자연어 대신 `/sns` 명령어로 부른다:

| 명령어 | 동작 |
|---|---|
| `/sns <키워드>` | 키워드로 콘텐츠를 찾는다. 1건이면 바로 진행, 여러 건이면 제목을 번호로 나열하고 번호를 받는다 |
| `/sns <번호>` | 직전에 제시한 후보 목록에서 그 번호의 콘텐츠로 진행한다 |
| `/sns <키워드> <플랫폼>` | 특정 플랫폼만 만든다 (threads, instagram, linkedin) |

**후보가 여러 건이면 반드시 제목 목록을 먼저 보낸다.** 비슷한 콘텐츠가 많아 오작성을 막는 장치다. 1건일 때만 되묻지 않고 진행한다.

**링크에는 유입 추적 파라미터를 붙인다.** 어느 채널에서 왔는지 구분하는 장치다:

| 플랫폼 | 링크 |
|---|---|
| 쓰레드 | `<글 URL>?ref=thd` |
| 링크드인 | `<글 URL>?ref=lkdn` |
| 인스타그램 | 링크를 넣지 않는다 (본문 링크가 클릭되지 않는 플랫폼) |

## 1. 대상 글 찾기

사용자는 보통 "젠스파크 글 SNS 작성해줘"처럼 일부만 말한다. 검색으로 확정한다:

```bash
cd /Users/osomahong/orca/projects/hongblog
node .claude/skills/sns-writer/scripts/find_post.mjs "젠스파크"   # 키워드 검색 (insight, class, course 전체)
node .claude/skills/sns-writer/scripts/find_post.mjs --latest 5   # "최근 글", "어제 쓴 글"
node .claude/skills/sns-writer/scripts/find_post.mjs --pending 5  # SNS를 아직 안 만든 최근 콘텐츠 (주간 루틴이 쓴다)
node .claude/skills/sns-writer/scripts/find_post.mjs --slug <slug> # 본문까지 가져오기
```

검색은 insight, class, course를 모두 본다. 결과의 `type` 필드로 종류를 구분한다. class는 제목이 `term`, course는 코스 이름이 `title`에 담겨 나온다.

- 검색 결과가 1건이면 그대로 진행한다. 되묻지 않는다.
- 2건 이상이면 제목을 번호로 나열하고 어느 글인지 묻는다. 텔레그램이면 이 질문도 텔레그램으로 보낸다.
- 0건이면 `--latest 5`를 보여주며 이 중에 있는지 묻는다.

확정한 뒤 `--slug`로 본문 전체를 읽는다. **본문을 읽지 않고 제목과 발췌만으로 쓰지 않는다.**
카피에 들어갈 구체적 사실(수치, 조건, 날짜)이 본문에만 있기 때문이다.

## 2. 소재 고르기

**목적은 두 가지다: 본문이 읽고 싶어져서 블로그에 들어오게 하는 것, 그리고 팔로워를 모으는 것.**
블로그 본문을 다 옮기는 것이 목적이 아니다. 체계적으로 전부 정리하면 읽는 사람은
다 배웠다고 느끼고 떠나며, 글이 깊어질수록 피드에서는 지루해진다.

그래서 소재는 **본문에서 가장 재미있는 2~3개만** 고른다. 기준은 재미다:

- **의외성**: 예상과 반대인 것. 기본값이 꺼져 있다, 로컬 앱인데 데이터가 밖으로 나간다
- **손해 회피**: 모르면 돈이나 시간을 잃는 것. `highlights` 필드가 대개 여기에 해당한다
- **바로 써먹는 꿀팁**: 오늘 실무에 옮길 수 있는 사용 예시 하나

나머지는 버린다. 구성 요소 나열, 조건 목록, 배경 설명, 기술 구조처럼
체계적이지만 재미없는 부분이 블로그가 맡을 몫이다. "자세한 설정 순서는 정리해 뒀습니다"로
넘기는 것이 이 스킬에서는 올바른 마무리다.

고른 소재마다 정보의 핵심(결론)은 카피에서 주되, 그 주변(왜 그런지, 어떻게 하는지의
세부)은 블로그로 남긴다. 핵심까지 감추면 낚시가 되고, 세부까지 다 주면 들어올 이유가 없다.

**콘텐츠 종류마다 소재 잡는 축이 다르다.**

- **insight**: 위 기준 그대로다. `highlights` 필드와 본문의 의외성, 꿀팁에서 2~3개를 고른다.
- **class(용어 정의)**: 용어 하나를 쉽게 풀어 주는 것이 축이다. "이 용어 헷갈리셨죠"류 훅으로 열고, `definition`을 미끼로 주되 실무에서 언제 쓰는지 세부는 블로그로 남긴다. 용어 하나가 주제라 카드뉴스로 특히 잘 맞는다.
- **course(코스 개요)**: 커리큘럼을 다 나열하지 않는다. "이 순서로 배우면 된다"는 학습 경로 하나와, 이 코스를 마치면 무엇을 할 수 있게 되는지를 축으로 잡는다. 목차 일부만 후킹에 쓰고 전체는 블로그로 남긴다.

## 3. 두 벌 쓰기

`references/platforms.md`의 플랫폼별 규격과 구조를 따른다. 요약하면:

- **쓰레드**: 합쇼체, 훅 1편 + 본문 2~4편의 **짧은 체인**. 두괄식이 절대 규칙이라 첫 줄에 가장 자극적인 사실을 그대로 꺼낸다. 각 편은 아이디어 하나만 다루고 120~350자에서 끊는다. `1/`, `2/` 번호를 붙이고 링크(`?ref=thd`)는 마지막 편에
- **인스타그램**: 한 편으로 닫는다. 첫 125자가 생명(더보기 전에 보이는 구간). 해요체로 가볍게 정리하고 해시태그 3~5개와 저장 유도를 끝에 붙인다. 링크 없음
- **링크드인**: 한 편, 합쇼체. 실무자의 업무가 어떻게 달라지는지를 축으로 쓴다. 첫 200자 안에 결론을 넣고, 본문은 짧은 문단 3~4개, 끝에 링크(`?ref=lkdn`)와 해시태그 3~5개

**쓰레드에 반말을 쓰지 않는다.** 일상 잡담 계정은 반말이 기본이지만 이 계정은 정보성 계정이고,
같은 분야에서 잘 도는 계정들은 전부 합쇼체를 쓴다. 반말은 정보의 무게를 깎는다.

문체는 `references/writing-rules.md`를 지킨다. 특히 이 셋은 매번 확인한다:
이모지 게시물당 2개 이하, 느낌표 1개 이하, 본문에 없는 사실 추가 금지.

쓰기 전에 두 레퍼런스를 모두 읽는다. 기억으로 쓰면 규칙이 흐려진다.

## 4. 자기 검수

**규격은 스크립트로 센다.** 글자 수와 해시태그 개수를 눈으로 세면 매번 틀린다:

```bash
cd /Users/osomahong/orca/projects/hongblog
node .claude/skills/sns-writer/scripts/check_copy.mjs threads   <파일>   # 체인 파일은 편마다 검사
node .claude/skills/sns-writer/scripts/check_copy.mjs instagram <파일>
```

쓰레드 체인은 `---`로 편을 구분해 한 파일에 담으면 편별로 나눠 검사한다.
글자 수, 해시태그, 이모지, 느낌표, 번역투, 과장 표현, 어미 3연속, 반말 종결을 잡는다.

**판단이 필요한 것은 사람이 본다.** 스크립트가 통과시켜도 아래는 직접 확인한다:

- `references/writing-rules.md`의 자기 검수 질문 다섯 개
- **첫 게시물 첫 줄만 읽고도 유용한 사실 하나가 남는가.** 두괄식이 무너지면 체인 전체가 안 읽힌다
- 각 본문 편이 해석 한 줄로 닫히는가
- 사실 대조: 카피의 수치와 고유명사를 본문에서 찾아 일치하는지 본다. 본문에 없으면 지운다. 애매하면 덜 구체적으로 쓴다

## 5. 이미지 준비

텍스트만 주지 않는다. 플랫폼별로 함께 올릴 이미지를 챙겨서 카피와 같이 전달한다.

**기존 자원부터 확인한다** (새로 만들기 전에):

- 썸네일: `public/og/<slug>.png` (블로그 OG 이미지. 쓰레드 훅 편, 링크드인에 그대로 쓸 수 있다)
- 본문 이미지: `public/images/insights/<slug>/` (도표, 스크린샷. 쓰레드 본문 편에 붙이기 좋다)

**인스타는 카드뉴스를 생성한다.** 인스타는 이미지가 본체라 캡션만 주면 올릴 수 없다.

카드 배경은 **실사 사진을 기본**으로 한다. 그래픽만 있는 카드보다 피드에서 눈에 잘 잡힌다.
사진은 fetch_photo.mjs로 웹에 공개된 무료 라이선스 이미지를 받아 쓴다:

```bash
cd /Users/osomahong/orca/projects/hongblog
node .claude/skills/sns-writer/scripts/fetch_photo.mjs "<영문 검색어>" <저장경로.jpg>   # Openverse, 키 불필요
node .claude/skills/sns-writer/scripts/fetch_photo.mjs "<검색어>" --candidates 5       # 후보만 보기
node .claude/skills/sns-writer/scripts/make_cards.mjs <cards.json> <출력디렉터리>
```

사진 고르는 기준:

- **적당히 연관되면 충분하다.** 주제를 그대로 묘사할 필요 없고 메타포가 오히려 좋다. 환각이면 안개 낀 길, 추측이면 주사위, 검증이면 돋보기.
- 카드마다 다른 사진을 쓴다. 검색어는 영문으로, 구체적인 사물 위주로 잡는다.
- **받은 사진을 Read로 직접 열어 확인한다.** 무기, 정치, 특정 인물이 담긴 사진은 버리고 다시 검색한다. 자동으로 받아지는 물건이라 눈으로 거르는 단계가 필수다.
- 라이선스: CC0/PDM이면 그대로, CC-BY면 함께 생성되는 `.attribution.json`의 출처를 사용자에게 전달하고 인스타 캡션 끝에 "Photo: 작가명 (CC BY)" 표기를 권한다.

카드 구성:

- cover 1장 + content 3~4장 + last 1장. 총 5~6장. 1080x1350(4:5).
- 실사 배경 위에 어두운 오버레이와 흰 글자, 블로그 톤의 빨강/금색 포인트가 자동 적용된다. `photo` 필드를 빼면 플랫 디자인으로 나온다.
- cover의 title은 카피의 훅과 같은 메시지를 쓰되 11자 안팎으로 줄을 나눈다.
- content 카드는 쓰레드 체인의 편 구성을 재활용하면 빠르다. 편당 카드 하나, body는 한 줄 12자 안팎으로 짧게.
- last 카드는 행동 유도(원문 열기, 저장)와 프로필 링크 안내를 담는다.
**카드 문구도 문체 게이트를 통과해야 한다.** 카드는 글자 수가 적어 비문이 더 도드라진다.
렌더링 전에 반드시 거친다:

1. cards.json의 title/heading/body/cta를 텍스트 파일로 뽑아 기계 검사를 돌린다:
   ```bash
   node .claude/skills/prose-inspector/scripts/check-literary.mjs <추출한 파일>
   ```
2. `prose-inspector` 스킬의 낭독 검수를 카드 문장에도 적용한다. 카드에서 특히 잘 깨지는 유형:
   - **주어-서술어 호응**: "답은 원문을 여세요"(여는 대상이 답인지 원문인지 붕괴) → "답은 원문과 대조하세요"
   - **주어 누락**: "nano는 3.1%입니다"(무엇이 3.1%인지 없음) → "환각률은 nano가 3.1%"
   - **'~일수록' 오용**: 비교 축이 없는데 붙이는 경우. "조작된 인용일수록 형식이 완벽합니다" → "조작된 인용은 형식이 완벽합니다"
   - 줄바꿈 때문에 생기는 문제: 조사나 짧은 어절("받으면")이 한 줄에 홀로 남으면 문장을 다시 짠다
3. 렌더링 후 카드를 Read 도구로 직접 열어 소리 내어 읽는다. 텍스트가 잘리거나 사진과 겹쳐 안 읽히면 cards.json을 고쳐 다시 만든다.

쓰레드/링크드인용 목업이나 도표가 따로 필요하면 같은 방식(SVG 작성 → resvg 렌더링)으로 만든다.

## 6. 결과 전달

**텔레그램에서 온 요청이면 결과를 반드시 텔레그램으로 보낸다.** 터미널에만 출력하면
요청자는 아무것도 받지 못한다. `reply` 도구를 쓰고 `chat_id`는 인바운드 메시지의 값을 그대로 넘긴다.

메시지는 **그대로 복사해 올릴 단위마다 따로** 보낸다. 여러 편을 한 메시지에 합치면
사용자가 잘라내야 해서 불편하다. 쓰레드 체인은 편마다 게시물이 되므로 편마다 한 메시지다.

**메시지에 라벨을 붙이지 않는다.** `[쓰레드 훅]`, `[인스타그램]` 같은 머리말을 달면
복사할 때 지워야 한다. 메시지 본문은 게시할 텍스트 그대로만 담는다. 순서만 봐도
무엇인지 알 수 있고, 마지막 안내 메시지에서 구성을 설명하면 충분하다.

- 첫 메시지: 짧은 안내 (몇 번째 메시지가 어느 플랫폼인지 한두 줄)
- 이어서: 쓰레드 각 편 (본문만. `1/`, `2/` 번호는 게시물에 실제로 들어가는 것이라 남긴다)
- 이어서: 인스타 캡션 (본문만)
- 이어서: 링크드인 (본문만)
- 마지막 메시지: 쓰레드 태그 제안, 고른 소재 한 문장

체인이 길어 메시지가 6~7개가 되어도 나눠 보낸다. 복사 편의가 우선이다.

**이미지도 함께 보낸다.** 텔레그램 sendPhoto(또는 reply 도구의 files)로 전송한다:

- 카드뉴스는 순서대로 전부, 캡션 없이 (받아서 그대로 인스타에 올리는 물건)
- OG 썸네일과 본문 이미지는 캡션에 용도를 한 줄 적는다 ("쓰레드 훅에 첨부 추천")

**쓰레드 태그는 카피 본문에 넣지 않는다.** 쓰레드는 게시할 때 태그를 따로 입력하는
구조이고 `#` 기호도 쓰지 않는다. 본문에 `#태그`를 박아 두면 그대로 복사했을 때
지저분해지므로, 세 번째 메시지에 "태그 제안: AI 도구 보안"처럼 따로 적어 준다.

`format`은 기본값 `text`를 쓴다. `markdownv2`는 이스케이프가 필요해 카피 안의
괄호나 마침표가 깨진다. 카피는 사용자가 그대로 복사해 붙일 물건이므로 원문 그대로 보내는 것이 중요하다.

터미널 세션에서 온 요청이면 그냥 화면에 출력한다. 이때도 플랫폼별로 구분해 보여 준다.

## 7. 이력 기록

**카피를 다 전달한 뒤 반드시 이력을 남긴다.** 주간 루틴이 같은 콘텐츠를 다시 후보로 올리지 않게 하는 장치다. 만든 플랫폼과 오늘 날짜를 함께 기록한다:

```bash
cd /Users/osomahong/orca/projects/hongblog
node .claude/skills/sns-writer/scripts/sns_log.mjs --add <slug> --date <YYYY-MM-DD> [threads instagram linkedin]
```

- 플랫폼 인자를 생략하면 세 종 전부 만든 것으로 기록한다. 특정 플랫폼만 만들었으면 그 이름만 넣는다.
- 날짜는 오늘 날짜를 넣는다. 세션에 주어진 현재 날짜를 그대로 쓴다.
- 나중에 같은 콘텐츠를 다시 만들고 싶으면 `--remove <slug>`로 이력을 지워 후보에 다시 노출시킨다.

## 8. 수정 요청 처리

"쓰레드 좀 더 짧게", "인스타 훅 바꿔줘" 같은 후속 요청이 오면 해당 플랫폼만 다시 써서
그 하나만 보낸다. 양쪽을 다시 보내면 어느 것이 최신인지 헷갈린다.

"둘 다 다시"라고 하면 소재 선택부터 바꿔 본다. 같은 소재로 문장만 바꾸면
사용자가 느낀 문제가 그대로 남는 경우가 많다.
