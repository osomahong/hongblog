# sns-writer

블로그 글 하나를 쓰레드, 링크드인, 인스타그램 세 벌의 카피로 옮긴다.
**같은 글이라도 플랫폼마다 글은 완전히 달라야 한다.** 길이만 줄인 같은 문장을
여러 곳에 올리면 어느 채널에서도 성과가 나지 않는다.

## 플랫폼별 우선순위

실측이 순서를 정한다. 링크드인 유입이 세션당 5.47페이지에 체류 20분으로 가장 깊고,
쓰레드가 그다음이며, 인스타는 유입이 아니라 인지를 맡는다.
**쓰레드와 링크드인을 먼저 쓰고 공을 들인다.** 인스타는 카드뉴스로 가볍게 간다.

플랫폼별 톤과 규격은 `references/platforms.md`, 문체 규칙은 `references/writing-rules.md`,
이 계정에서 실제로 통한 것은 `references/playbook.md`에 있다.
**쓰기 전에 세 문서를 모두 읽는다.** 기억으로 쓰면 규칙이 흐려진다.

`platforms.md`는 플랫폼 일반론이고 `playbook.md`는 준이아빠블로그 계정의 실측이다.
둘이 어긋나면 **playbook을 따른다.** 일반론보다 이 계정에서 나온 결과가 앞선다.

Buffer로 올릴 때는 `references/buffer-publishing.md`를 먼저 읽는다.
즉시 발행(`shareNow`)은 쓰지 않고 초안이나 예약으로만 보낸다.

사용자가 특정 플랫폼만 지목하면 그것만 쓴다. 지목이 없으면 **2번 채널 판정을 먼저 하고**
해당하는 채널만 만든다. 세 벌을 무조건 다 만들지 않는다.

## 말투 게이트 (생략 불가, 2026-08-25 사고로 추가)

**이 스킬의 문서만 읽고 카피를 쓰면 실패한다.** 이 스킬은 규격(길이, 체인, 해시태그, 링크, 게시 시각)을
정하고, **말투는 `~/.claude/skills/hongsh-voice/`가 정한다.** 카톡 5개월치 17,337건에서 뽑은
본인 말투 팩이다. 규격과 말투가 어긋나면 규격은 이 스킬, 말투는 hongsh-voice를 따른다.

2026-08-25에 실제로 있었던 일이다. 이 스킬만 로드하고 쓰레드 카피를 만들었더니 합쇼체 9줄에
해요체 0줄, 15줄 가운데 14줄이 마침표로 끝나고, 🧵 이모지가 붙고, 개성 장치가 하나도 없고,
마지막 편이 "정리해 뒀습니다"로 닫힌 카피가 나갔다. `check_copy.mjs`와 hongblog 문체 검사 두 개는
전부 HARD 0건으로 통과시켰다. **규격 통과와 문어체 사전 통과는 말투 통과가 아니다.**
사용자 지적: "hongblog 지침을 어겼고 RAG에서 내 SNS 대화 스타일을 반영하지 않은 듯함".

원인은 두 스킬이 서로를 한 방향으로만 가리킨 것이다. hongsh-voice는 "규격은 sns-writer"라고
적어 두었는데 sns-writer는 hongsh-voice를 한 번도 부르지 않았다. 그래서 아래를 절차에 박는다.

지어내지 않는다. 본문에 담긴 판단은 글쓴이 것이므로 1인칭으로 옮길 수 있다.

### 쓰레드 카피의 고정값 (10-tone-threads 요약)

- **첫 줄은 판단이나 사건 선언이다.** "쓸 이유가 없음", "업계 뒤집어질 ~가 나왔음", "충격을 받았습니다". **"~분들 보세요" 같은 대상 지정으로 열지 않는다.** 2026-08-25 사용자가 공유한 고성과 5건과 10배 차이 난 대조군(playbook P7)에서 확정
- **첫 편에 구체 수치 셋 이상**(돈, 개수, 성과)과 **읽는 사람의 지갑 이야기**(무료, 얼마 아낌, 광고비 태움)를 넣는다
- **한 줄에 사실 하나.** 접속사로 잇지 않는다. **반말은 음슴체("~음", "~함", "~임")까지 포함해 쓰지 않는다.** 2026-08-25 사용자 결정: 존대로도 충분히 SNS 스타일이 된다. "쓸 이유가 없음"은 "지금은 결제할 이유가 없어요"로
- **해요체가 기본.** 판단과 근거 문장 한두 줄만 합쇼체로 올리고, 유보는 다시 해요체로 내린다. 다만 말투는 성패 변수가 아니다(P2, P7). 구조가 먼저다
- **마침표는 짧은 선언 줄에서만.** 설명 줄은 줄바꿈으로 끊는다. 한 줄 30~50자
- **이미지는 주장 한 장.** 아이콘에 X, 큰 글자 한 줄 카드, 실제 설정 화면. 설명용 캡처 두 장보다 세다
- **신분이나 성과로 말할 자격을 먼저 보인다.** "현직 ~인데", "9년 차 마케터인데". 본문에 근거가 있는 것만
- **이모지 0개.** 🧵 예고도 붙이지 않는다
- **개성 장치 최소 하나.** 통념 세우고 치기(`다들 ~하시죠`), 반문, 호불호 선언, 가상 대사, 동기 폭로
- **1편은 도입부가 아니라 가장 센 본론.** 배경 설명과 답 없는 질문으로 열지 않는다
- **착지는 논리 결론이 아니라 구체 장면이나 짧은 고백**
- **마지막 편은 목적에 따라 다르다.** 대화가 목적이면 경험 질문 한 줄, **유입이 목적이면 미공개 항목을 이름으로 짚는 티저.** 마무리는 `정리해봤습니다`(겸양 합쇼체)이고 `정리해 뒀습니다`, `정리해놨어요`는 쓰지 않는다
- **가르치지 않는다.** "~하라고 합니다"가 아니라 "저는 ~하는 쪽이에요"
- `거에요` 표기는 쓰레드까지 유지한다. 인스타와 링크드인은 표준 표기

### 검사 (기계가 강제한다)

`check_copy.mjs`가 규격 검사 뒤에 **hongsh-voice의 `check_voice.mjs`를 자동으로 호출한다.**
검사기를 찾지 못하면 통과시키지 않는다. 표준입력(`-`)으로는 말투 검사를 돌릴 수 없으므로 파일로 저장해 돌린다.

말투 검사가 HARD로 잡는 것: 마침표 종결 20% 초과, 합쇼체가 해요체보다 많음, 이모지, 구어 완료형
마무리, 거예요 표기, 문어체 사전 위반. SOFT로 알리는 것: 개성 장치 없음, 유입 목적인데 질문으로 닫힘,
가르치는 말투, 문장 65자 초과, 체인 순서.

**HARD 0건이 아니면 사용자에게 보여 주지 않는다.** 통과한 뒤 `10-tone-threads.md` 끝의 눈 검사 셋
(첫 두 줄만 읽어도 무슨 얘기인지, 마지막 줄이 장면인지, 판단 뒤에 유보가 있는지)을 본다.

## 0. 부르는 방법과 대상

**대상 콘텐츠는 세 종류다.** insight(인사이트 글), class(용어 정의), course(코스 개요) 모두 SNS로 옮긴다. 종류마다 소재를 잡는 방식이 달라서 2번 소재 고르기에서 나눠 다룬다.

**명령어 규격.** 텔레그램에서는 자연어 대신 `/sns` 명령어로 부른다:

| 명령어 | 동작 |
|---|---|
| `/sns <키워드>` | 키워드로 콘텐츠를 찾는다. 1건이면 바로 진행, 여러 건이면 제목을 번호로 나열하고 번호를 받는다 |
| `/sns <번호>` | 직전에 제시한 후보 목록에서 그 번호의 콘텐츠로 진행한다 |
| `/sns <키워드> <플랫폼>` | 특정 플랫폼만 만든다 (threads, linkedin, instagram) |

**후보가 여러 건이면 반드시 제목 목록을 먼저 보낸다.** 비슷한 콘텐츠가 많아 오작성을 막는 장치다. 1건일 때만 되묻지 않고 진행한다.

**링크에는 `ref` 하나만 붙인다.** utm은 붙이지 않는다. GA4 이벤트 수정 규칙이
`page_location`의 `ref` 값을 직접 읽도록 세팅되어 있다. (2026-08-24 갱신)

| 플랫폼 | 링크 |
|---|---|
| 쓰레드 | `<글 URL>?ref=thd` |
| 링크드인 | `<글 URL>?ref=lkdn` |
| 인스타그램 | 링크를 넣지 않는다. `링크는 프로필에 있어요.`로 안내한다 (`ref=ig`는 프로필 링크 쪽) |
| 카카오톡 | `<글 URL>?ref=ok`. SNS 카피가 아니라 채팅방에 직접 올릴 때만 쓴다 |

`utm_campaign`에는 한글을 넣지 않는다. GA4에서 일부가 깨져 들어온다. 슬러그를 그대로 쓴다.

## 1. 대상 글 찾기

사용자는 보통 "젠스파크 글 SNS 작성해줘"처럼 일부만 말한다. 검색으로 확정한다.
스크립트는 자기 위치에서 프로젝트 루트를 잡으므로 어느 경로에서 실행해도 된다:

```bash
node ${CLAUDE_SKILL_DIR}/scripts/find_post.mjs "젠스파크"    # 키워드 검색 (insight, class, course 전체)
node ${CLAUDE_SKILL_DIR}/scripts/find_post.mjs --latest 5    # "최근 글", "어제 쓴 글"
node ${CLAUDE_SKILL_DIR}/scripts/find_post.mjs --pending 5   # SNS를 아직 안 만든 최근 콘텐츠
node ${CLAUDE_SKILL_DIR}/scripts/find_post.mjs --slug <slug> # 본문까지 가져오기
```

검색은 insight, class, course를 모두 본다. 결과의 `type` 필드로 종류를 구분한다. class는 제목이 `term`, course는 코스 이름이 `title`에 담겨 나온다.

- 검색 결과가 1건이면 그대로 진행한다. 되묻지 않는다.
- 2건 이상이면 제목을 번호로 나열하고 어느 글인지 묻는다. 텔레그램이면 이 질문도 텔레그램으로 보낸다.
- 0건이면 `--latest 5`를 보여주며 이 중에 있는지 묻는다.

확정한 뒤 `--slug`로 본문 전체를 읽는다. **본문을 읽지 않고 제목과 발췌만으로 쓰지 않는다.**
카피에 들어갈 구체적 사실(수치, 조건, 날짜)이 본문에만 있기 때문이다.

## 2. 채널 판정: 이 글을 어디에 올릴지 먼저 정한다

**카피를 쓰기 전에 이 판정을 먼저 한다.** 소재가 맞지 않으면 훅을 아무리 고쳐도 반응이 없다.

### 쓰레드에 올릴 글

쓰레드에서 읽히는 글은 **개인이 지금 당장 써먹거나 아끼는 것**이다.
한국어 쓰레드 고성과 게시물 16건이 전부 여기 해당했다.

| 신호 | 뜻 | 준이아빠블로그 예 |
|---|---|---|
| **돈 아낌** | 무료, 가격 인하, 요금제 | 클로드 아카데미 무료 강좌, GPT 가격 인하 |
| **바로 써먹음** | 사용법, 꿀팁, 자동화 | Orca 사용법, 클로드 자동화 |
| **도구 판단** | 써볼지 말지, 비교, 후기 | Orca와 VS Code 비교, 모델 비교 |
| **직접 돌림** | 설치, 로컬 실행 | 맥에서 로컬 모델 돌리기, CLI 설치 |

네 신호 가운데 하나도 없으면 쓰레드 카피를 만들지 않는다.

### 쓰레드에 올리지 않을 글

**B2B 의사결정과 방법론은 쓰레드에서 읽히지 않는다.** 업체 선정, 계약, 측정 설계,
전략 프레임워크가 여기 해당한다. 준이아빠블로그 154편 중 30편이 이 부류이고
검색에서도 8월 조회가 20회에서 260회 사이로 낮다.

쓰레드에서 마케팅 계정을 오래 운영한 사람의 관찰이 같은 이야기를 한다.

> 마케터의 글을 보는 사람은 사업하시는분, 자영업하시는분, 그리고 마케터입니다.
> 스레드 전체 파이 중 위 세 파이는 적습니다. (220좋아요 게시물)

이런 글은 **링크드인만 만든다.** 실명 피드에는 그 판단을 읽을 사람이 있다.

| 업체 선정, 계약 | **X** | O | X |
| 측정 설계, 방법론 | **X** | O | X |
| 업계 동향, 관점 | 세모 | O | X |
| 용어 정의 (class) | 세모 | X | O |

**검색 성과와 쓰레드 적합도는 별개다.** 검색에서 잘 되는 도구 글이 쓰레드에서도 잘 된다.
실제로 쓰레드에서 Orca 주제로 414좋아요와 453좋아요를 받은 게시물이 있는데,
준이아빠블로그는 Orca 글이 조회수 2위이면서 쓰레드에 올린 적이 없다.

## 3. 소재 고르기

**목적은 두 가지다: 본문이 읽고 싶어져서 블로그에 들어오게 하는 것, 그리고 팔로워를 모으는 것.**
블로그 본문을 다 옮기는 것이 목적이 아니다. 체계적으로 전부 정리하면 읽는 사람은
다 배웠다고 느끼고 떠나며, 글이 깊어질수록 피드에서는 지루해진다.

그래서 소재는 **본문에서 가장 재미있는 2~3개만** 고른다. 기준은 재미다:

- **의외성**: 예상과 반대인 것. 기본값이 꺼져 있다, 로컬 앱인데 데이터가 밖으로 나간다
- **손해 회피**: 모르면 돈이나 시간을 잃는 것. `highlights` 필드가 대개 여기에 해당한다
- **바로 써먹는 꿀팁**: 오늘 실무에 옮길 수 있는 사용 예시 하나

나머지는 버린다. 구성 요소 나열, 조건 목록, 배경 설명, 기술 구조처럼
체계적이지만 재미없는 부분은 준이아빠블로그 본문이 맡는다. "자세한 설정 순서는 정리해 뒀습니다"로
넘기는 것이 이 스킬에서는 올바른 마무리다.

고른 소재마다 정보의 핵심(결론)은 카피에서 주되, 그 주변(왜 그런지, 어떻게 하는지의
세부)은 블로그로 남긴다. 핵심까지 감추면 낚시가 되고, 세부까지 다 주면 들어올 이유가 없다.

**플랫폼마다 고르는 소재가 다르다.** 같은 글에서 세 벌을 뽑되 재료를 나눈다.

| 플랫폼 | 고르는 것 |
|---|---|
| 쓰레드 | 의외성과 꿀팁. 피드에서 눈이 멈추는 사실 |
| 링크드인 | 업무가 어떻게 달라지는지, 도입할 만한지에 대한 판단 |
| 인스타 | 용어 하나 또는 단계 하나. 카드로 쪼갤 수 있는 것 |

**검색이 이미 잘 가져오는 주제는 SNS에서 반복하지 않는다.** 노코드, 자동화, 바이브코딩,
AI 태그는 편당 조회가 495회를 넘어 구글이 알아서 데려온다. SEO, 데이터 분석,
퍼포먼스마케팅은 20~41회로 검색이 못 가져오므로 SNS가 메울 자리다.
태그별 수치와 코스 목록은 `playbook.md` 1번에 있다.

**코스는 개별 클래스가 아니라 묶음으로 소개한다.** 코스 허브로 들어온 방문이
세션당 7.56페이지를 만든다. 클래스 한 편만 링크하면 그 한 장만 보고 나간다.

**콘텐츠 종류마다 소재 잡는 축도 다르다.**

- **insight**: 위 기준 그대로다. `highlights` 필드와 본문의 의외성, 꿀팁에서 2~3개를 고른다.
- **class(용어 정의)**: 용어 하나를 쉽게 풀어 주는 것이 축이다. `definition`을 미끼로 주되 실무에서 언제 쓰는지 세부는 블로그로 남긴다. 용어 하나가 주제라 카드뉴스로 특히 잘 맞는다.
- **course(코스 개요)**: 커리큘럼을 다 나열하지 않는다. "이 순서로 배우면 된다"는 학습 경로 하나와, 이 코스를 마치면 무엇을 할 수 있게 되는지를 축으로 잡는다.

## 4. 세 벌 쓰기

`references/platforms.md`의 플랫폼별 톤과 구조를 따른다. 요약하면:

**쓰레드**: **해요체 기본, 판단 한 줄만 합쇼체, 마침표 없음, 이모지 없음** (말투 게이트 참고).
훅 1편 + 본문 2~4편의 짧은 체인. 두괄식이 절대 규칙이라 첫 줄에 가장 센 사실을 그대로 꺼낸다.
첫 줄에 숫자, 의외성, 통념 뒤집기 중 하나가 반드시 있어야 한다. 각 편은 아이디어 하나만 다루고
120~350자에서 끊는다. `1/`, `2/` 번호를 붙이고 링크는 마지막 편에. **마지막 편은 목적에 따라
경험 질문 한 줄(대화) 또는 미공개 항목 티저(유입)로 닫고, 마무리는 `정리해봤습니다`다.**

**링크드인**: 텍스트 한 편, 합쇼체, 500~700자. 도구가 아니라 업무 변화로 연다.
첫 200자 안에 결론을 넣고, 짧은 문단 3~4개로 끝낸다. **판단을 담는 문단이 반드시 하나 있어야 한다**
("다만", "대신"이 들어갈 자리). 끝에 열린 질문 한 문장, 링크, 해시태그 3~5개.
**이미지는 붙이지 않는다.** 단일 이미지는 텍스트 전용보다 참여가 30% 낮다.

**인스타그램**: 카드뉴스가 본체, 캡션은 보조. 첫 125자가 생명이다.
해요체로 가볍게 정리하고 해시태그 3~5개와 저장 유도를 끝에 붙인다. 링크 없음.

**쓰레드에 반말을 쓰지 않는다.** 다만 합쇼체로 통일하지도 않는다. 2026-08-24에 hongsh-voice
`10-tone-threads.md`에서 해요체 기본으로 개정했다(본인 구어 기본값이 해요체 32.5%, 합쇼체 3.3%이고
실측 답글 최다 게시물이 해요체). 관찰은 해요체, 판단은 합쇼체, 유보는 해요체로 오르내린다.

**사용자의 시그니처 접속어를 쓴다.** 판단을 쓰는 대목에서 "하지만", "그러나"를 먼저 떠올리지 말고
"다만", "대신", "실제로"를 쓴다. 준이아빠블로그 본문에서 각각 151회, 122회, 166회 쓰인 표현이고
카피가 사용자 글처럼 읽히게 하는 핵심이다.

문어 레지스터(링크드인)는 `references/writing-rules.md`를 지킨다. 쓰레드와 인스타의 말투는
hongsh-voice가 기준이다(말투 게이트 참고). 채널 불문 매번 확인하는 것:
이모지 0개(쓰레드), 느낌표 1개 이하, 본문에 없는 사실 추가 금지, 답 없는 첫 줄 질문 금지.

## 5. 자기 검수

**규격은 스크립트로 센다.** 글자 수와 해시태그 개수를 눈으로 세면 매번 틀린다:

```bash
node ${CLAUDE_SKILL_DIR}/scripts/check_copy.mjs threads   <파일>   # 체인 파일은 편마다 검사
node ${CLAUDE_SKILL_DIR}/scripts/check_copy.mjs linkedin  <파일>
node ${CLAUDE_SKILL_DIR}/scripts/check_copy.mjs instagram <파일>
```

`check_copy.mjs`는 규격을 본 뒤 **hongsh-voice `check_voice.mjs`를 자동으로 부르고, 그 안에서 hongblog
문어체 사전(`prose-inspector/check-literary.mjs`)까지 돈다.** 말투 HARD가 있으면 규격이 맞아도 실패다.

쓰레드 체인은 `---`로 편을 구분해 한 파일에 담으면 편별로 나눠 검사한다.
글자 수, 해시태그, 이모지, 느낌표, 번역투, 과장 표현, 어미 3연속, 반말 종결,
utm 파라미터, 첫 줄 질문, 마지막 질문 유무를 잡는다.

**판단이 필요한 것은 사람이 본다.** 스크립트가 통과시켜도 아래는 직접 확인한다:

- `references/writing-rules.md`의 자기 검수 질문 일곱 개
- **첫 게시물 첫 줄만 읽고도 유용한 사실 하나가 남는지.** 두괄식이 무너지면 체인 전체가 안 읽힌다
- 링크드인에 판단 문단이 실제로 들어 있는지. 요약만 있으면 다시 쓴다
- 마지막 질문이 의견이 아니라 경험을 묻고 있는지
- 사실 대조: 카피의 수치와 고유명사를 본문에서 찾아 일치하는지 본다. 본문에 없으면 지운다. 애매하면 덜 구체적으로 쓴다

## 6. 이미지 준비

**링크드인에는 이미지를 붙이지 않는다.** 도표가 정보를 실제로 더 주는 경우에만 예외다.

**쓰레드**는 편마다 도표나 스크린샷 1장을 붙이면 좋다. 기존 자원부터 확인한다:

- 썸네일: `public/og/<slug>.png` (쓰레드 훅 편에 쓸 수 있다)
- 본문 이미지: `public/images/insights/<slug>/` (도표, 스크린샷)

**인스타는 카드뉴스를 생성한다.** 이미지가 본체라 캡션만 주면 올릴 수 없다.

카드 배경은 **실사 사진을 기본**으로 한다. 그래픽만 있는 카드보다 피드에서 눈에 잘 잡힌다.

```bash
node ${CLAUDE_SKILL_DIR}/scripts/fetch_photo.mjs "<영문 검색어>" <저장경로.jpg>   # Openverse, 키 불필요
node ${CLAUDE_SKILL_DIR}/scripts/fetch_photo.mjs "<검색어>" --candidates 5       # 후보만 보기
node ${CLAUDE_SKILL_DIR}/scripts/make_cards.mjs <cards.json> <출력디렉터리>
```

사진 고르는 기준:

- **적당히 연관되면 충분하다.** 주제를 그대로 묘사할 필요 없고 메타포가 오히려 좋다. 환각이면 안개 낀 길, 추측이면 주사위, 검증이면 돋보기.
- 카드마다 다른 사진을 쓴다. 검색어는 영문으로, 구체적인 사물 위주로 잡는다.
- **받은 사진을 Read로 직접 열어 확인한다.** 무기, 정치, 특정 인물이 담긴 사진은 버리고 다시 검색한다.
- 라이선스: CC0/PDM이면 그대로, CC-BY면 함께 생성되는 `.attribution.json`의 출처를 사용자에게 전달하고 인스타 캡션 끝에 "Photo: 작가명 (CC BY)" 표기를 권한다.

카드 구성:

- cover 1장 + content 3~4장 + last 1장. 총 5~6장. 1080x1350(4:5).
- **디자인은 사용자가 준 레퍼런스 5장을 따른다 (2026-08-24).** 테두리, 드롭섀도, 색 배지
  박스는 쓰지 않는다. 사진은 카드 전체를 어둡게 깔지 않고, 위쪽은 사진 그대로 두고 글이
  앉는 아래 구간만 완전한 검정으로 끊는다. `photo` 필드를 빼면 카드 전체가 검정이다.
  번호와 킥커는 박스 없이 작은 금색 글자로만 쓴다. 본문 중 정말 중요한 한 줄은
  `highlight`(content) / `cta`(cover, last) 필드로 지정하면 금색 형광펜 바를 글자
  뒤에 깐다(떠 있는 배지가 아니라 그 줄의 글자 폭에 붙는 바탕색).
- cover의 title은 카피의 훅과 같은 메시지를 쓰되 11자 안팎으로 줄을 나눈다.
- content 카드는 쓰레드 체인의 편 구성을 재활용하면 빠르다. 편당 카드 하나.
- last 카드는 저장 유도와 프로필 링크 안내를 담는다. handle(URL)은 금색 형광펜 바로 강조된다.

**카드 문구도 문체 게이트를 통과해야 한다.** 규칙 전문은 `references/card-text-rules.md`에 있고,
글을 쓰기 전에 읽는다. 핵심만 옮기면:

- **필드 성격에 따라 문체가 다르다 (2026-08-24 갱신).** `kicker`/`number`는 짧은 라벨이라
  그대로 둔다. `title`/`heading`은 hongblog 헤딩 관례대로 명사구로 닫는다
  (`막히는 곳은 GA4 계정`). `body`/`cta`/`note`/`highlight`는 **간결한 합쇼체 문장**으로
  쓴다 — "GA4 계정 없으면 화면도 못 봄"이 아니라 "GA4 계정이 없으면 화면조차 볼 수
  없습니다."로. 개조식으로 먼저 정했다가, 문장이 뚝뚝 끊겨 읽힌다는 지적을 받고 뒤집었다.
- **줄바꿈은 문장 경계에서만.** `\n` 한 줄 = 완결된 합쇼체 문장 하나다. 문장 중간을
  끊어 다음 줄로 넘기지 않는다. 카드 하나에 문장 2~3개를 넘기지 않는다("간결한"이 핵심).
- **카드마다 대상을 다시 말한다.** 인스타는 한 장씩 넘겨 보므로 앞 카드의 주어가 이어지지 않는다.
  "화면이 처음이면 초급"이 아니라 "GA4 화면이 처음이면 초급"이다.

`make_cards.mjs`와 `make_thumb.mjs`가 그리기 전에 `check_cards.mjs`를 자동으로 부르고,
HARD가 있으면 그리지 않는다. 따로 돌려 볼 수도 있다:

```bash
node ${CLAUDE_SKILL_DIR}/scripts/check_cards.mjs <cards.json>
node ${CLAUDE_SKILL_DIR}/scripts/check_cards.mjs --text "킥커" "제목" "부제"
```

검사기는 hongblog 공용 문어체 사전(`prose-inspector/check-literary.mjs`)을 그대로 부른 뒤
개조식 규칙을 얹는다. 사전을 여기에 복사하지 않는다.

**기계가 못 보는 것은 낭독으로 잡는다.** 검사기가 마지막에 항목을 찍어 준다.
주어 누락과 목적어에 안 쓰는 동사가 카드에서 가장 자주 깨진다.

렌더링 후 카드를 Read 도구로 직접 열어 소리 내어 읽는다. 검사기는 글자만 보고 사진은 못 본다.
글자가 사진의 밝은 부분과 겹쳐 안 읽히면 사진을 바꾼다.

**칸을 넘는 디자인이 나오면 안 된다.** 렌더러가 글자 폭을 폰트에서 재서 색 상자를 만들고,
안 들어가면 글자를 줄이고, 다 줄여도 안 되면 멈춘다. 그래도 렌더 후 눈으로 한 번 더 본다.

## 7. Buffer 예약

`references/buffer-publishing.md`를 읽고 진행한다. 순서를 지킨다:

```bash
node ${CLAUDE_SKILL_DIR}/scripts/buffer_post.mjs --channels                       # 채널 목록과 연결 상태
node ${CLAUDE_SKILL_DIR}/scripts/buffer_post.mjs --plan <post.json>               # 예약 계획만 출력
node ${CLAUDE_SKILL_DIR}/scripts/buffer_post.mjs --send <post.json> --confirm     # 실제 예약
```

**게시 전에 카피 전문을 사용자에게 출력하고 승인을 받는다.** 글 배포 게이트와 같은 방식이다.
SNS 게시물은 지워도 캡처가 남아 되돌리기 어렵다. `--confirm` 없이는 전송되지 않는다.

**연결이 끊긴 채널은 게시가 조용히 실패한다.** `--channels`로 `isDisconnected`를 먼저 확인한다.
링크드인은 60일, 쓰레드는 90일마다 Buffer 화면에서 다시 인증해야 한다.

예약 시각은 사람이 화면을 보는 시간으로 잡는다. 쓰레드는 첫 30분 반응이 도달을 정하고
링크드인은 업무 시간에 읽힌다.

| 플랫폼 | 권장 시각 |
|---|---|
| 쓰레드 | 평일 오전 8~9시, 점심 직후 1시 전후 |
| 링크드인 | 평일 오전 8~10시, 화요일에서 목요일 |
| 인스타그램 | 평일 저녁 7~9시 |

쓰레드 체인은 편 순서대로 몇 분 간격을 두고 예약한다. 같은 시각에 몰면 순서가 섞인다.

## 8. 결과 전달

**텔레그램에서 온 요청이면 결과를 반드시 텔레그램으로 보낸다.** 터미널에만 출력하면
요청자는 아무것도 받지 못한다. `reply` 도구를 쓰고 `chat_id`는 인바운드 메시지의 값을 그대로 넘긴다.

메시지는 **그대로 복사해 올릴 단위마다 따로** 보낸다. 여러 편을 한 메시지에 합치면
사용자가 잘라내야 해서 불편하다. 쓰레드 체인은 편마다 게시물이 되므로 편마다 한 메시지다.

**메시지에 라벨을 붙이지 않는다.** `[쓰레드 훅]`, `[인스타그램]` 같은 머리말을 달면
복사할 때 지워야 한다. 메시지 본문은 게시할 텍스트 그대로만 담는다.

- 첫 메시지: 짧은 안내 (몇 번째 메시지가 어느 플랫폼인지 한두 줄)
- 이어서: 쓰레드 각 편 (본문만. `1/`, `2/` 번호는 게시물에 실제로 들어가는 것이라 남긴다)
- 이어서: 링크드인 (본문만)
- 이어서: 인스타 캡션 (본문만)
- 마지막 메시지: 쓰레드 태그 제안, 고른 소재 한 문장, 예약 시각 제안

**이미지도 함께 보낸다.** 텔레그램 sendPhoto(또는 reply 도구의 files)로 전송한다:

- 카드뉴스는 순서대로 전부, 캡션 없이 (받아서 그대로 인스타에 올리는 물건)
- 쓰레드용 도표는 캡션에 용도를 한 줄 적는다 ("쓰레드 2편에 첨부 추천")
- 링크드인용 이미지는 보내지 않는다

**쓰레드 태그는 카피 본문에 넣지 않는다.** 쓰레드는 게시할 때 태그를 따로 입력하는
구조이고 `#` 기호도 쓰지 않는다.

`format`은 기본값 `text`를 쓴다. `markdownv2`는 이스케이프가 필요해 카피 안의
괄호나 마침표가 깨진다.

터미널 세션에서 온 요청이면 그냥 화면에 출력한다. 이때도 플랫폼별로 구분해 보여 준다.

## 9. 이력과 실험 기록

**카피를 다 전달한 뒤 반드시 이력을 남긴다.** 주간 루틴이 같은 콘텐츠를 다시 후보로 올리지 않게 하는 장치다:

```bash
node ${CLAUDE_SKILL_DIR}/scripts/sns_log.mjs --add <slug> --date <YYYY-MM-DD> [threads linkedin instagram]
```

- 플랫폼 인자를 생략하면 세 종 전부 만든 것으로 기록한다. 특정 플랫폼만 만들었으면 그 이름만 넣는다.
- 날짜는 세션에 주어진 현재 날짜를 그대로 쓴다.
- 다시 만들고 싶으면 `--remove <slug>`로 이력을 지워 후보에 다시 노출시킨다.

**`playbook.md`의 실험 기록표에도 행을 추가한다.** 성과 칸은 비워 두고 조건만 적는다.
어떤 훅 유형, 어떤 소재 유형, 링크 유무, 마지막 질문 유무로 썼는지가 나중에 판정의 근거가 된다.
조건을 적지 않으면 2주 뒤에 성과만 남고 원인을 알 수 없다.

## 10. 성과 회수와 다음 실험

2주에 한 번 돌린다. 이 단계가 있어야 스타일이 개선된다.

```bash
node ${CLAUDE_SKILL_DIR}/scripts/sns_perf.mjs --days 30 --by-campaign
node ${CLAUDE_SKILL_DIR}/scripts/sns_perf.mjs --days 30 --merge
```

1. 회수한 값으로 `playbook.md` 4번 표의 성과 칸을 채운다. 쓰레드 답글 수는 GA4에 잡히지 않으므로 화면에서 직접 센다.
2. 2번 가설 중 게시물 4건 이상에서 같은 방향이 반복된 것이 있으면 3번 검증된 패턴으로 올린다. 뒤집혔으면 결과를 적고 지운다.
3. 다음 2주 계획에서 **변수 하나만** 바꾼다. 순서는 링크 유무, 마지막 질문, 소재 유형, 훅 유형이다.

**한 번에 여러 변수를 바꾸지 않는다.** 성과가 올라도 무엇 때문인지 모르면 다음에 재현할 수 없다.

## 11. 수정 요청 처리

"쓰레드 좀 더 짧게", "링크드인 훅 바꿔줘" 같은 후속 요청이 오면 해당 플랫폼만 다시 써서
그 하나만 보낸다. 양쪽을 다시 보내면 어느 것이 최신인지 헷갈린다.

"둘 다 다시"라고 하면 소재 선택부터 바꿔 본다. 같은 소재로 문장만 바꾸면
사용자가 느낀 문제가 그대로 남는 경우가 많다.
