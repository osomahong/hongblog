Open Code Review는 알리바바가 사내에서 쓰다가 오픈소스로 공개한 AI 코드리뷰 명령줄 프로그램입니다. `ocr` 명령으로 실행하면 Git 변경분을 읽어 줄 단위로 지적 사항을 답니다.

AI에게 코드리뷰를 맡기는 방식은 이미 익숙합니다. 클로드 코드나 코덱스에 변경분을 보여 주고 문제를 찾아 달라고 하면 답이 나오고, 그 결과를 커밋 전에 확인하는 사람도 늘었습니다.

덜 알려진 쪽은 그 결과가 얼마나 일정한지입니다. 비교할 만한 장면이 있습니다. 공항 검색대에서는 모든 가방이 예외 없이 X선 장비를 지납니다. 범용 에이전트에 리뷰를 맡기면 변경 파일 몇 개는 그냥 건너뛸 수 있고, 지적한 줄 번호가 실제 위치와 어긋나는 경우도 생깁니다. 공식 문서와 공개된 벤치마크를 근거로 2026년 9월 16일 기준으로 정리합니다.

![Open Code Review 공식 저장소의 요약 수치. 사내 활성 사용자 20K+, 실제 수행한 코드리뷰 작업 3M+, 최근 30일 npm 다운로드 329K+, 클로드 코드 대비 토큰 비용 1/9, AACR-Bench 점수 25.10%가 나열되어 있다](/images/insights/alibaba-open-code-review-guide/highlights-en.png)

## 알리바바 사내 도구가 공개된 배경

이 프로그램은 알리바바 그룹 안에서 AI 코드리뷰용으로 2년 넘게 쓰였습니다. 공식 설명에 따르면 사내 개발자 수만 명이 사용했고 그동안 찾아낸 결함이 수백만 건입니다. 그 기록을 바탕으로 알리바바가 2026년 5월 저장소를 공개했습니다.

공개 이후 반응은 숫자로 확인됩니다. 2026년 9월 16일 기준 깃허브 별은 30,686개인데, 같은 날 오전에 조회한 값이 28,596개였으니 하루에도 수천 개씩 붙고 있습니다. npm 패키지의 최근 30일 내려받기는 329,386건입니다.

읽는 쪽 문턱도 낮습니다. 한국어 README가 함께 있어 원문을 영어나 중국어로 읽지 않아도 됩니다. 라이선스는 Apache-2.0이라 사내 도입 심사에서 걸리는 경우가 드뭅니다. 구현 언어는 Go이고 설치는 npm으로 합니다.

## 범용 에이전트에 리뷰를 맡길 때 생기는 문제 세 가지

공식 문서는 클로드 코드에 스킬을 붙여 리뷰를 맡겼을 때 겪는 문제를 세 가지로 정리합니다.

- **변경분을 다 보지 않습니다.** 변경 파일이 많아지면 일부만 골라 보고 나머지를 지나치는 일이 생깁니다.
- **위치가 어긋납니다.** 지적한 줄 번호나 파일 이름이 실제 문제 위치와 맞지 않는 경우가 있습니다.
- **품질이 들쭉날쭉합니다.** 자연어 지시로만 움직이면 문구를 조금 바꿔도 결과가 달라지고, 왜 그런지 따져 보기 어렵습니다.

원인으로 지목된 것은 모델 성능이 아니라 구조입니다. 리뷰 절차 전체를 말로만 시키면 반드시 거쳐야 할 단계를 못 박아 둘 방법이 없습니다.

## 검사 절차와 모델 판단을 나눈 구조

이 프로그램의 설계는 두 부분으로 나뉩니다. 모든 가방을 장비에 통과시키는 일은 기계가 맡고 열어 볼지 말지만 따로 판단하듯, 틀리면 안 되는 단계는 코드로 고정하고 판단이 필요한 단계만 모델에 넘깁니다.

코드로 고정한 쪽은 이렇습니다.

- **파일 선택**: 어떤 파일을 봐야 하고 어떤 파일을 걸러야 하는지 프로그램이 정합니다.
- **파일 묶기**: 서로 관련된 파일을 한 묶음으로 만들어 하위 에이전트에 넘깁니다. 번역 파일 두 개처럼 짝이 되는 파일이 함께 검토됩니다.
- **규칙 연결**: 파일 성격에 맞는 검토 규칙만 골라 붙여 모델이 볼 내용을 줄입니다.
- **위치와 내용 재검토**: 지적한 위치가 맞는지, 내용이 타당한지를 각각 별도 모듈이 다시 확인합니다.

모델에 맡긴 쪽은 상황에 따라 달라지는 판단을 내리는 일과 필요한 맥락을 찾아오는 일입니다. 이때 쓰는 지시문과 도구 묶음은 코드리뷰에 맞춰 다듬은 것입니다. 공식 문서는 실제 사용 기록에서 호출 빈도와 반복률을 분석해 이 묶음을 정리했다고 설명합니다.

## 클로드 코드와 비교한 벤치마크 수치

AACR-Bench는 인기 오픈소스 저장소 50개에서 실제 풀 리퀘스트 200건을 뽑아 10개 언어로 구성한 벤치마크입니다. 시니어 엔지니어 80여 명이 교차 검증한 이슈 1,505건을 정답지로 삼았습니다.

![AACR-Bench 순위표. 1위는 Open Code Review와 Claude-4.6-Opus 조합으로 F1 25.10%, 정밀도 33.90%, 재현율 20.00%, 평균 소요 시간 1분 23초, 385K 토큰이고, Claude Code 조합 가운데 9위와 12위를 보면 F1 14.13%와 11.57%, 평균 소요 시간 5분 38초와 13분 6초, 2,062K와 5,664K 토큰을 기록했다](/images/insights/alibaba-open-code-review-guide/benchmark-en.png)

같은 모델을 쓴 조합만 뽑아 비교하면 차이가 분명해집니다.

| 조합 | F1 | 정밀도 | 재현율 | 평균 시간 | 평균 토큰 |
|---|---|---|---|---|---|
| 클로드 4.6 오퍼스 + Open Code Review | 25.10% | 33.90% | 20.00% | 1분 23초 | 385K |
| 클로드 4.6 오퍼스 + 클로드 코드 | 11.57% | 7.23% | 28.90% | 13분 6초 | 5,664K |

정밀도는 지적한 항목 가운데 실제 결함의 비율이고, 재현율은 실제 결함 가운데 찾아낸 비율입니다. 표를 보면 두 조합이 잘하는 부분이 서로 다릅니다. 전용 도구 쪽은 지적의 적중률이 높고 시간과 토큰을 적게 쓰지만, 범용 에이전트 쪽은 결함을 더 많이 찾아냅니다. 공식 문서는 재현율이 낮은 것을 잘못 지적한 항목을 걸러내는 시간을 줄이려는 의도된 절충이라고 밝힙니다. 모든 파일을 검토 대상에 넣는 것과 결함을 다 찾아내는 것은 다른 이야기입니다.

토큰 배수도 기준에 따라 다릅니다. 공식 저장소가 내세우는 9분의 1은 풀 리퀘스트 1,000건을 평균한 값이고, 위 표의 같은 모델 비교만 놓고 보면 15분의 1 수준입니다.

이 수치를 읽을 때 조심할 점이 두 가지 있습니다.

첫째, **이 수치는 프로그램을 만든 쪽이 측정한 값입니다.** 자체 벤치마크를 공개했다는 점은 확인되지만, 제3자가 같은 조건으로 재현한 결과는 아직 공개되지 않았습니다.

둘째, **1위 조합의 F1도 25.10%입니다.** 정밀도 33.90%와 재현율 20.00%를 하나로 묶은 값이라, 지적 셋 가운데 하나만 실제 결함이고 실제 결함 다섯 가운데 넷은 그냥 지나간다는 뜻입니다. 어느 쪽을 골라도 사람 검토를 대신할 수준은 아니므로, 먼저 훑어 주는 도구로 두고 놓친 것이 있다는 전제로 쓰는 편이 안전하다고 생각합니다.

## 설치와 첫 실행 명령

준비물은 Git 2.41 이상입니다. npm 전역 설치 한 번으로 끝나고, 스크립트나 깃허브 릴리스 파일을 쓰는 방법도 문서가 함께 안내합니다.

```bash
npm install -g @alibaba-group/open-code-review
```

설치하면 `ocr` 명령을 쓸 수 있습니다. 리뷰를 돌리기 전에 제공자와 모델을 고르고 API 키를 넣으면, 연결이 되는지 자동으로 확인해 줍니다.

```bash
ocr config provider   # 제공자를 고르거나 직접 추가
ocr config model      # 고른 제공자의 모델 선택
```

![Open Code Review의 모델 제공자 선택 화면. 터미널에 Official, Custom, Manual 탭이 있고 그 아래 알리바바 DashScope, 앤트로픽 클로드, DeepSeek, Kimi Moonshot, OpenAI, Z.AI 등 제공자 13개가 목록으로 나열되어 화살표로 고르게 되어 있다](/images/insights/alibaba-open-code-review-guide/providers.jpg)

설정을 마치면 저장소에서 바로 실행합니다. `review`와 `scan` 두 명령을 아래 네 가지로 씁니다.

```bash
ocr review                                  # 스테이징, 미스테이징, 미추적 변경을 모두 검토
ocr review --from main --to feature-branch  # 분기 지점 이후 변경만 검토
ocr review --commit abc123                  # 커밋 하나만 검토
ocr scan --path internal/agent              # 변경분이 아니라 파일 전체를 검토
```

마지막 `scan`은 처음 보는 저장소를 살필 때 쓰는 명령입니다. Git 이력이 없어도 되고 디렉터리를 지정할 수 있어서, 넘겨받은 코드를 훑을 때 쓸 만합니다.

결과를 파일로 남기려면 형식과 출력 경로를 지정합니다.

```bash
ocr review --format json --output result.json
```

## 위임 모드로 API 키 없이 쓰는 방법

이 도구를 쓰려면 별도 모델 요금이 든다고 생각하기 쉬운데, 위임 모드를 쓰면 그렇지 않습니다.

위임 모드는 **파일 선택과 규칙 연결만 이 도구가 맡고 실제 리뷰는 원래 쓰던 코딩 에이전트가 자기 모델로 수행하는 방식**입니다. 클로드 코드 구독을 이미 쓰고 있다면 API 키를 따로 넣지 않아도 됩니다.

```bash
ocr delegate preview
ocr delegate rule src/main.go src/handler.go
```

클로드 코드와 코덱스, 커서, 오픈코드에서 쓰는 플러그인이 저장소에 함께 들어 있어서, 에디터 안에서 슬래시 명령으로 리뷰를 부를 수도 있습니다. 깃허브 액션과 깃랩 CI 연동 문서도 제공됩니다.

## 자주 묻는 질문

### Open Code Review는 클로드 코드를 대신하나요?

역할이 다릅니다. 클로드 코드는 코드를 작성하고 고치는 도구이고, Open Code Review는 변경분을 검토하는 한 가지 일만 합니다. 위임 모드를 쓰면 두 프로그램을 함께 쓰게 되므로 둘 가운데 하나를 고르는 문제로 보지 않아도 됩니다.

### 한국어 코드 주석이나 변수명도 검토되나요?

10개 언어로 벤치마크했다고 할 때의 언어는 프로그래밍 언어입니다. 자연어 처리는 쓰는 모델의 능력을 따라가므로, 한국어 주석이 섞인 저장소에서는 결과가 어떻게 나올지 직접 돌려 확인하는 편이 확실합니다.

### 회사 코드를 외부로 보내는 것이 걱정되면 어떻게 하나요?

실제로 리뷰하는 것은 여러분이 설정한 모델입니다. 사내 규정상 외부 API로 코드를 보낼 수 없다면 사내에 올린 모델을 제공자로 지정하거나, 이미 승인받은 코딩 에이전트에 넘기는 위임 모드를 쓰는 선택지가 있습니다. 어느 쪽이든 실제 전송 경로를 먼저 확인하는 것이 좋습니다.

## 3줄 요약

- Open Code Review는 알리바바가 사내에서 2년 넘게 쓰다가 2026년 5월 Apache-2.0 라이선스로 공개한 AI 코드리뷰 명령줄 프로그램입니다.
- 파일 선택과 규칙 적용은 코드로 고정하고 판단만 모델에 맡기는 구조여서, 자체 벤치마크에서 같은 모델을 쓴 클로드 코드보다 정밀도가 높고 토큰은 약 9분의 1만 썼습니다.
- 재현율은 범용 에이전트보다 낮은 쪽으로 만들었고 1위 조합의 F1도 25.10%에 그치므로, 사람 검토를 대체하는 도구가 아니라 먼저 훑는 도구로 두는 편이 맞습니다.
