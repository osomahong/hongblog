Orca가 무엇이고 어떻게 설치하는지는 [지난 글](/insights/orca-ide-easy-guide)에서 다뤘습니다. 쉽게 말하면, VS Code 같은 기존 도구가 코드 편집에 특화된 개발 프로그램(IDE)이라면 Orca는 AI를 많이 쓰고 동시에 쓰기 위한 목적으로 만들어진 **AI 시대의 컨트롤 타워**입니다. 클로드 코드, 코덱스 같은 코딩 AI 여러 개를 분리된 작업 공간에서 동시에 돌리는 무료 공개 프로그램입니다. 이번 글은 그 다음 이야기입니다. 화면을 처음 열면 VS Code와 비슷하게 생겼는데, 실제로 써 보면 다른 물건입니다. 어디가 다르고, 썼을 때 무엇이 좋아지고, 어떤 현실적인 한계가 있는지 정리합니다.

## 어디가 VS Code와 비슷하고 어디가 다를까요?

비슷하게 느껴지는 이유는 실제로 익숙한 구성 요소를 그대로 품고 있기 때문입니다. VS Code 계열 편집기(자동 저장 지원), 파일 탐색기, 터미널, 빠른 검색(퀵 오픈)이 모두 들어 있어서, 파일을 열고 수정하는 기능은 VS Code와 크게 다르지 않습니다.

다른 것은 화면의 중심 단위입니다.

| 구분 | VS Code | Orca |
|------|---------|------|
| 화면의 중심 | 파일과 편집기 | 에이전트 세션과 작업 공간(워크트리) |
| 사이드바가 보여주는 것 | 폴더 구조 | 어떤 AI가 무슨 일을 하고 있는지 |
| AI의 위치 | 확장 기능으로 덧붙임 | 프로그램의 존재 이유 |
| 사람의 역할 | 코드를 직접 작성 | 일을 나눠 주고 결과를 검토 |

VS Code에서 AI는 편집기에 덧붙은 부가 기능이지만, Orca에서는 AI가 중심이고 편집기가 그 곁에 딸려 있는 구조입니다. 그래서 Orca의 장점도 "편집이 편리하다"가 아니라 "여러 AI에게 시킨 일을 관리하기 편리하다" 쪽에 몰려 있습니다.

## 프로젝트 관리는 어떤 점이 편할까요?

에이전트를 2개 이상 쓰기 시작하면 관리 문제가 생깁니다. 누가 일하는 중이고 누가 내 확인을 기다리는지, 결과물 중 무엇을 채택할지를 사람이 머릿속으로 추적해야 합니다. Orca는 이 부분에 화면을 제일 많이 씁니다.

- **세션 상태 추적**: 사이드바에서 각 에이전트가 작업 중인지, 멈춰서 입력을 기다리는지 한눈에 보입니다. 읽지 않은 응답에는 표시가 붙습니다.
- **GitHub와 Linear 내장**: PR과 이슈 목록, 프로젝트 보드를 Orca 안에서 바로 봅니다. 이슈를 보다가 그 자리에서 에이전트에게 작업을 넘기는 흐름이 됩니다.
- **diff에 주석 달아 되돌려주기**: AI가 고친 코드의 변경 내역(diff)에 사람이 인라인 주석을 달면, 그 주석이 다시 에이전트에게 지시로 전달됩니다. 코드 리뷰하듯 AI와 주고받는 방식입니다.
- **계정과 사용량 추적**: 클로드, 코덱스 계정을 여러 개 등록해 전환하고, 남은 사용량을 프로그램 안에서 확인합니다.

위 두 화면이 Orca 공식 저장소에 실린 실제 프로젝트 보드와 diff 리뷰 화면입니다. VS Code였다면 브라우저(GitHub), 이슈 트래커, 편집기를 오가며 처리하던 일이 Orca에서는 한 화면에 모입니다.

## 기능은 얼마나 들어 있을까요?

설정 화면을 열어 보면 켤 수 있는 기능이 많습니다. 대표적인 기능만 추리면 다음과 같습니다.

- **디자인 모드(Design Mode)**: 내장 브라우저에서 화면 요소를 클릭하면 그 요소의 HTML, CSS, 스크린샷이 에이전트 프롬프트에 자동으로 들어갑니다. "이 버튼 색을 바꿔 줘"를 말로 설명할 필요가 없어집니다.
- **컴퓨터 유즈(Computer Use)**: 설정에서 켜면 에이전트가 화면에 보이는 데스크톱 앱과 브라우저를 직접 조작할 수 있습니다.
- **자체 오케스트레이션 도구**: Orca CLI로 에이전트가 작업 공간 생성, 화면 캡처, 클릭, 입력까지 스크립트로 실행할 수 있어, AI가 Orca 자체를 조종하는 구성이 가능합니다. 스킬 등록과 MCP 연결, 작업 공간 생성 시 자동 실행되는 훅도 지원하고, 저장소의 `.claude/`, `.codex/` 설정을 그대로 읽어 갑니다.
- **휴대폰 연결**: QR 코드를 찍으면 iOS, 안드로이드 앱이 데스크톱과 짝을 이룹니다. 에이전트가 일을 마치면 푸시 알림이 오고, 밖에서 진행 상황을 확인하고 지시를 보낼 수 있습니다.
- **원격 작업 공간(SSH)**: 성능 좋은 원격 서버에서 에이전트를 돌리고 화면은 내 컴퓨터에서 보는 구성을 지원합니다.

![Orca 데스크톱과 휴대폰 앱이 연결된 화면. 폰 화면에 소환한 에이전트 수 1,284개, 연결된 MacBook Pro와 Mac Mini, 이어서 작업할 워크트리와 페어링 버튼이 표시됨](/images/insights/orca-vs-vscode/orca-mobile-companion.jpg)

![Orca의 디자인 모드 화면. 내장 브라우저에 웹사이트가 열려 있고 오른쪽에 파일 탐색기가 나란히 표시된 모습](/images/insights/orca-vs-vscode/orca-design-mode.jpg)

이런 기능이 Orca의 장점입니다. 유료 AI 편집기들이 예고만 해 온 기능(디자인 모드 등)을 무료 공개 프로그램이 먼저 내놓은 사례도 있어서, UX에 공을 들인다는 평가가 커뮤니티에서 나오는 편입니다.

## 현실적인 한계는 무엇일까요?

장점만 보고 시작하면 겪게 되는 한계도 있습니다.

- **가볍지 않습니다**: 설치 파일이 250MB 수준이고, 에이전트 몇 개를 띄운 상태의 대기 메모리가 400~800MB에 이른다는 실측 리뷰가 있습니다. 세션과 터미널을 많이 열수록 무거워지는 구조라, 사양이 낮은 컴퓨터에서는 체감 속도가 떨어질 수 있습니다.
- **병렬 실행은 사용량도 병렬로 씁니다**: 클로드 코드를 3개 동시에 돌리면 구독 사용량도 3배로 소모됩니다. 이걸 모르고 쓰다가 한도에 일찍 도달했다는 사례들이 있습니다. 여러 세션에 걸친 사용량을 한눈에 보여주는 기능은 아직 부족하다는 지적도 있습니다.
- **폰 앱은 데스크톱이 켜져 있어야 합니다**: 휴대폰 연결은 데스크톱 세션의 리모컨이라서, 노트북을 덮으면 폰에서도 볼 수 없습니다.
- **업데이트가 잦은 만큼 버그도 잦습니다**: 거의 매일 새 버전이 나오는 속도라 기능과 함께 오류도 실려 오는 편입니다. 안정성이 중요하면 특정 버전에 머무르는 운영이 권장되고 있습니다.
- **설정이 많은 것 자체가 진입 장벽입니다**: 컴퓨터 유즈, CLI, 훅, 원격 연결 모두 설정에서 직접 켜야 하고, 원격 작업 공간은 서버 쪽에 전용 설치가 필요합니다.
- **에이전트 사이의 순서 지정은 미완입니다**: "A가 계획하고 B가 테스트를 짜고 C가 구현한다"처럼 순서를 엮는 기능은 아직 완성되지 않았다는 평가가 있습니다.

## 그래서 어떻게 쓰기 시작하면 좋을까요?

기능이 많다고 처음부터 다 켤 필요는 없습니다. 단계를 나누면 이렇게 됩니다.

1. **관리 화면부터**: 에이전트 1~2개로 세션 상태 추적과 알림, diff 주석만 써 봐도 VS Code와의 차이를 체감할 수 있습니다. 이 단계는 사용량 부담도 적고 컴퓨터도 크게 무거워지지 않습니다.
2. **병렬은 필요할 때**: 기다리는 시간이 실제로 아까워질 때 세션을 늘립니다. 이때부터 사용량이 배수로 나간다는 점을 기억해 두면 됩니다.
3. **부가 기능은 하나씩**: 웹 화면을 만들 때 디자인 모드, 자리를 자주 비운다면 폰 연결처럼, 상황이 생겼을 때 해당 설정만 켜는 것이 관리하기 쉽습니다.

VS Code를 잘 쓰고 있고 에이전트도 하나만 쓴다면 지금 당장 갈아탈 이유는 없습니다. 에이전트가 둘 이상이 되어 관리 자체가 부담스러워지는 시점부터는, Orca의 장점이 무게(리소스), 설정, 사용량 같은 비용보다 커집니다.

**3줄 요약:**

- Orca는 VS Code처럼 편집기와 탐색기를 품고 있지만 화면의 중심이 파일이 아니라 에이전트 세션이라, 장점도 편집이 아니라 여러 AI 관리(상태 추적, GitHub와 Linear 내장, diff 주석)에 몰려 있습니다.
- 디자인 모드, 컴퓨터 유즈, 자체 오케스트레이션 CLI와 스킬, 휴대폰 연결, 원격 작업 공간까지 기능 폭이 넓고 UX 완성도가 좋다는 평가가 있습니다.
- 다만 세션을 많이 열수록 무거워지고, 병렬 실행은 구독 사용량을 배수로 소모하며, 잦은 업데이트에 버그가 실려 오는 편이라 관리 화면부터 작게 시작하는 것이 좋습니다.
