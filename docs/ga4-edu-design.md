# GA4 Edu 운영 설계

GA4 Edu를 뉴스레터 구독자 전용 학습 기능으로 운영하기 위한 접근 제어 방식과 학습 설계를 정리한 문서입니다. 커리큘럼 목록은 `ga4-edu-curriculum.md`에 있습니다.

## 0. 전제: 이미 있는 실습 엔진을 씁니다

GA4 Edu를 새로 짜지 않고, 이 저장소에 이미 만들어 둔 AIPBL 실습 엔진 위에 GA4 화면 미션만 얹습니다.

| 파일 | 하는 일 | GA4 Edu에서 쓰는 법 |
|---|---|---|
| `lab/LabShell.tsx` | 과제 확인, 미션, 점검, 정리 4단계 진행과 상단 스테퍼 | 그대로 재사용 |
| `lab/progress.ts` | localStorage 진행 저장, 이어서 하기 | 저장 키만 분리 |
| `lab/QuizPhase.tsx` | 선택형 점검과 즉시 해설 | 해석 문제로 내용만 교체 |
| `lab/BriefPhase.tsx` | 시작 화면, 지난 기록 표시 | 그대로 재사용 |
| `geo-basics/MockSiteViewer.tsx` | 가짜 사이트 화면 안에서 미션 수행 | GA4 화면 재현 컴포넌트의 본보기 |
| `ai-practice/data.ts` | 트랙과 단계 목록 데이터 | GA4 30개 목록으로 같은 형태 작성 |

기초, 중급, 심화 3단 구조와 트랙 개념도 같습니다. GA4 Edu는 AI-Practice의 세 번째 트랙에 가깝습니다.

## 1. 접근 제어: 뉴스레터 구독자 확인

뉴스레터는 스티비(`digitalmarketer.stibee.com`)로 운영 중이고, 지금 코드에는 인증 장치가 없습니다. 방식 세 가지를 비교했습니다.

| 방식 | 구현 부담 | 구독자 확인 정확도 | 문제점 |
|---|---|---|---|
| A. 회차 코드 입력 | 반나절 | 낮음 | 코드가 밖으로 퍼지면 막을 방법이 없음 |
| B. 이메일 확인 링크 + 스티비 명단 대조 | 2일에서 3일 | 높음 | 스티비 API 사용 조건 확인 필요 |
| C. 구글 로그인 + 데이터베이스 | 1주 이상 | 높음 | 구독 이메일과 구글 계정이 다르면 막힘 |

**B를 권합니다.** 학습자가 이메일을 넣으면 스티비 구독자 명단과 대조하고, 구독자면 확인 링크를 보내고, 링크를 누르면 서명된 쿠키를 30일간 심는 방식입니다. 구독자가 아니면 그 자리에서 구독 화면으로 보냅니다. 데이터베이스 없이 됩니다.

이 방식의 이점은 게이트가 곧 구독 유입 경로가 된다는 점입니다. 학습을 하려면 구독을 해야 하고, 구독자 명단은 스티비 한 곳에만 남습니다.

**먼저 확인해야 할 것**

- 스티비 API로 특정 이메일의 구독 여부를 조회할 수 있는지, 요금제 조건이 붙는지
- 조회가 안 되면 구독 신청 자체를 GA4 Edu 안에서 받고(스티비 구독자 추가 API), 신청 즉시 열어 주는 방식으로 바꿀 수 있음

**A를 임시로 쓰는 방법도 있습니다.** 스티비 확인이 늦어지면 회차 코드로 먼저 열고, 나중에 B로 교체합니다. 코드는 뉴스레터 본문에만 싣고 월 단위로 바꿉니다.

## 2. 전부 잠그지 않기

전부 잠그면 검색 유입이 끊깁니다. GA4 Edu 페이지가 색인되지 않으면 새 구독자가 들어올 길도 함께 막힙니다.

층을 셋으로 나눕니다.

| 층 | 범위 | 색인 | 목적 |
|---|---|---|---|
| 공개 | 튜토리얼 목록, 공개 2편 전체 | 색인함 | 검색 유입, 맛보기 |
| 게이트 | 나머지 28편. 과제 확인 화면까지 보이고 시작 버튼에서 막음 | 색인 안 함 | 구독 전환 |
| 구독자 전용 | 결과 요약 저장, 요약 카드 내려받기 | 색인 안 함 | 유지 |

공개 2편은 초급 1번(유입 정보 분석)과 중급 1번(자유 형식 보고서 만들기)입니다. 고른 이유는 `ga4-edu-curriculum.md`의 공개 2편 절에 적었습니다.

게이트를 만나는 지점은 세 번째 편의 시작 버튼입니다. 두 편을 끝까지 해 본 학습자라 화면의 쓸모를 이미 확인한 뒤이고, 여기서 구독 요청이 가장 잘 통합니다.

잠긴 편도 과제 확인 화면과 의뢰인 질문까지는 보여 줍니다. 무엇을 배우는지 모르는 상태에서 구독을 요구하면 이탈이 큽니다.

## 3. 체류시간 설계

### 3.1 클릭만 따라가는 튜토리얼을 만들지 않습니다

정해진 순서대로만 누르는 튜토리얼에서는 학습자가 아무 판단도 하지 않고 끝까지 갈 수 있습니다. 진행 표시와 완료 도장만 남는 구조는 이 저장소에서 이미 두 번 폐기한 방식입니다.

경로와 판단을 나눕니다.

- **어디를 누를지는 레일 위에 둡니다.** GA4 화면이 낯선 사람이 헤매지 않게 다음 클릭 지점을 표시합니다.
- **무엇이라고 읽을지는 학습자가 정합니다.** 화면에 도착한 다음 "이 표에서 문제가 있는 채널은 어디인가요" 같은 판단을 묻고, 고른 결과에 따라 다음 화면이 달라집니다.

체류시간은 클릭 수가 아니라 판단하는 횟수에서 나옵니다.

### 3.2 틀릴 수 있게 만듭니다

선택이 전부 정답으로 흘러가면 긴장이 없습니다. 잘못 고르면 그 결과를 화면에 그대로 띄웁니다.

예를 들어 중급 7번(향상된 측정에서 개별 이벤트 끄기)에서 스크롤 이벤트를 끄면, 다음 화면에서 지난달까지 있던 스크롤 이벤트가 사라진 이벤트 보고서를 보여 줍니다. 그리고 되돌리는 미션으로 이어집니다. 설정 하나가 데이터에 남기는 흔적을 문장으로 설명하는 것보다 화면으로 보는 편이 오래 남습니다.

### 3.3 의뢰인을 세웁니다

매 튜토리얼을 가상 의뢰인의 질문으로 시작합니다.

> 준준상점 마케터: "지난달 매출은 그대로인데 광고비만 늘었어요. GA4에서 어디를 봐야 할까요?"

마지막 정리 단계의 산출물은 그 질문에 답하는 문단 하나입니다. 학습자가 직접 쓰고, 모범 답안과 나란히 놓고 비교합니다. 채점하지 않고 대조만 합니다. 자유 입력과 대조는 선택형 문제보다 머무는 시간이 깁니다.

### 3.4 계정 하나를 30개가 공유합니다

30개 튜토리얼이 전부 같은 가상 계정("준준상점")의 데이터를 씁니다. 초급 3번에서 본 이상한 추천 유입의 원인이 심화 4번(원치 않는 추천 제외)에서 밝혀지는 식으로 앞뒤를 잇습니다.

한 편씩 흩어진 실습보다 이어지는 사건이 다음 편을 열게 만듭니다. 튜토리얼 끝에 "이 숫자의 원인은 심화 4번에서 다룹니다" 같은 연결을 답니다.

### 3.5 숫자를 매번 바꿉니다

같은 튜토리얼을 다시 열면 데이터 씨앗값이 바뀌어 숫자가 달라집니다. 답을 외운 사람도 읽는 절차를 다시 밟아야 합니다. 재방문 학습이 성립하고, 사내 교육에서 여러 명이 동시에 풀 때 답 공유가 무의미해집니다.

### 3.6 반대로 묻는 문제

화면을 주고 조작을 시키는 문제만 내지 않습니다. 잘못 설정된 GA4 화면을 먼저 보여 주고 어디가 잘못됐는지 찾게 합니다. 심화 구간에 특히 맞습니다.

## 4. 학습 효과를 높이는 장치

| 장치 | 내용 | 구현 부담 |
|---|---|---|
| 이어서 하기 | 중간에 나갔다 오면 마지막 미션부터 재개 | 이미 있음(`progress.ts`) |
| 오답 다시 보기 | 점검에서 틀린 문항만 모아 정리 단계에 표시 | 낮음 |
| 요약 카드 내려받기 | 정리 단계 산출물을 이미지 한 장으로 저장 | 중간(`generate-og.ts` 방식 재사용) |
| 실무 적용 체크리스트 | 배운 것을 자기 GA4 계정에 적용하는 3줄 절차 | 낮음 |
| 관련 인사이트 연결 | 같은 주제를 다룬 기존 블로그 글로 이동 | 낮음 |
| 용어 풀이 툴팁 | 화면 안 GA4 용어에 마우스를 올리면 설명 표시 | 중간 |

배지와 점수판은 넣지 않습니다. 진행률을 포장하는 장치는 학습 시간을 늘리지 못합니다.

## 5. 측정 설계

GA4 교육 페이지를 GA4로 측정합니다. 실습 화면은 페이지 이동이 없어서 페이지뷰만으로는 참여도가 잡히지 않습니다. 이벤트로 잡아야 합니다.

기존 `sendGAEvent` 패턴을 그대로 쓰고, AIPBL 이벤트와 이름을 나눕니다.

| 이벤트 | 매개변수 | 보는 것 |
|---|---|---|
| `ga4edu_start` | `lab_id`, `level`, `resume_from` | 시작과 재개 비율 |
| `ga4edu_gate_view` | `lab_id`, `mission_index` | 게이트를 만난 지점 |
| `ga4edu_subscribe_click` | `lab_id` | 게이트에서 구독으로 넘어간 비율 |
| `ga4edu_decision` | `lab_id`, `step`, `choice`, `correct` | 학습자가 자주 틀리는 판단 |
| `ga4edu_mission_complete` | `lab_id`, `position` | 미션별 이탈 지점 |
| `ga4edu_complete` | `lab_id`, `quiz_score`, `duration_sec` | 완주율과 소요 시간 |

`ga4edu_decision`이 가장 중요합니다. 특정 문항의 오답률이 높으면 학습자가 어려워하는 것이 아니라 문제나 화면 설명이 잘못됐을 가능성이 큽니다. 시나리오를 고치는 근거가 됩니다.

이 데이터는 나중에 튜토리얼 소재로도 씁니다. 실제 학습자 행동을 다룬 화면이라 예시 데이터보다 설득력이 있습니다.

## 6. 실행 순서

3단계로 나눕니다. 각 단계는 따로 배포할 수 있습니다.

**1단계: 뼈대와 견본 1개**

- `/ga4-edu`를 튜토리얼 목록 페이지로 바꾸고, 실시간 대시보드는 `/ga4-edu/realtime`으로 옮김
- GA4 화면 재현 컴포넌트(왼쪽 메뉴, 기간 선택기, 보고서 표, 카드) 제작
- 공개 2편(초급 1번, 중급 1번)을 끝까지 완성해 형식을 확정
- 게이트 없이 공개

공개 2편을 먼저 만들면 두 가지가 함께 풀립니다. 표준 보고서 화면과 탐색 보고서 화면을 둘 다 만들게 되므로, 나머지 28편이 쓸 컴포넌트가 1단계에서 거의 다 나옵니다.

**2단계: 게이트와 초급 완성**

- 스티비 구독 확인 방식 결정과 구현
- 세 번째 편부터 게이트
- 초급 나머지 9편 완성

**3단계: 중급과 심화**

- 중급 10개, 심화 10개
- 판단 분기와 되돌리기 미션은 중급부터 넣음
- 격주 1개씩 뉴스레터로 공개 소식을 보내며 재방문 유도

## 7. 정해야 할 것

1. 스티비 API로 구독자 조회가 되는지 확인. 안 되면 A안(회차 코드)으로 시작
2. 30개를 한 번에 낼지, 격주로 하나씩 열어 재방문을 만들지
3. 가상 계정 이름과 업종. 이커머스로 하면 심화 8번(항목 보고서)까지 한 계정으로 덮임
4. 판단 분기를 몇 개 튜토리얼에 넣을지. 전부 넣으면 제작 부담이 두 배가 됨
