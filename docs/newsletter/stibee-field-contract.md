## 1. 주소록과 가입 항목

`digitalmarketer.stibee.com` 페이지로 내보냈지만, 스탠다드 전환으로 사이트 안 팝업 폼에서
`/api/subscribe`를 거쳐 Neon과 스티비에 동시에 넣는다. `MANUAL, confirmEmailYN=N` 호출이 즉시
구독 처리되는 것을 실측으로 확인했으므로 기술 전제는 충족된다.

## 2. 사용자 정의 필드

스티비에 만들 필드는 세 개다. `stibee_id`는 스티비가 부여하는 구독자 식별자라 필드가 아니라
Neon 컬럼으로 저장한다.

| 스티비 필드 키 | 타입 | 넣는 값 | 채우는 주체 |
|---|---|---|---|
| `goal` | 텍스트 | 관심 주제 허용값 하나 | 체크인 API |
| `signup_source` | 텍스트 | 구독 지점 값 | `/api/subscribe` |
| `welcome_token` | 텍스트 | 서명된 체크인 토큰 (URL에 그대로 들어가는 값) | 구독자 생성 시 |
| `industry` | 텍스트 | 산업군 허용값 | 가입 폼 (선택) |
| `job_role` | 텍스트 | 직무 허용값 | 가입 폼 (선택) |
| `years` | 텍스트 | 연차 구간 허용값 | 가입 폼 (선택) |

### 가입 폼 드롭다운 허용값

| 필드 | 허용값 |
|---|---|
| `industry` | `ecommerce`(이커머스), `agency`(대행사, 컨설팅), `saas-it`(IT, SaaS), `contents-media`(콘텐츠, 미디어), `education`(교육), `finance`(금융), `manufacturing`(제조, 유통), `public`(공공, 비영리), `etc`(기타) |
| `job_role` | `marketing`(마케팅), `data`(데이터 분석), `planning`(기획, PM), `dev`(개발), `design`(디자인), `sales`(영업, CS), `founder`(대표, 프리랜서), `etc`(기타) |
| `years` | `y0-2`(2년 이하), `y3-5`(3~5년), `y6-9`(6~9년), `y10`(10년 이상), `none`(해당 없음) |

광고성 수신 동의는 API 응답에 보이는 시스템 필드 `stb_ad_agreement`로도 존재한다. 추가 요청
본문에서 이 값을 넣을 수 있는지는 폼 구현 때 확인하고, 되지 않으면 스티비 쪽은 비워 두고 Neon
기록만 증빙으로 쓴다.

- Neon에는 `welcome_token`의 **해시만** 저장한다. 원문은 스티비 필드와 메일 링크에만 존재한다.
- 메일 본문 치환은 `$%goal%$` 형태의 사용자 정의 필드 메일머지를 쓴다.

### `goal` 허용값 (고정)

| 값 | 뜻 | 착지에서 안내할 다음 콘텐츠 |
|---|---|---|
| `ai-flow` | 새로 나오는 AI 흐름을 따라가고 싶다 | AI 모델, 도구 소식 인사이트 |
| `ai-work` | AI를 실무에 제대로 쓰고 싶다 | 업무 적용 인사이트, AI-Practice 프롬프트 실습 |
| `content-marketing` | 콘텐츠와 마케팅에 AI를 쓰고 싶다 | SEO, AEO, GEO 글, AI-Practice GEO 실습 |
| `build-automation` | AI로 직접 만들고 자동화하고 싶다 | AI 코딩 도구 글 |

### `signup_source` 허용값

CTA의 GA4 `location` 값과 같은 체계를 쓴다: `nav`, `nav_mobile`, `home`, `post_bottom`, `footer`.
스티비 페이지로 직접 가입한 경우는 `stibee_page`로 남긴다.

## 3. 체크인 URL 규칙

### 링크 형식 (메일에 들어가는 URL)

```
https://www.digitalmarketer.co.kr/api/newsletter/check-in
  ?goal=<goal 허용값>
  &c=<campaign>
  &t=<welcome_token>
```

- 링크는 착지 페이지가 아니라 **API로 직접** 향한다. API가 검증과 저장을 끝낸 뒤 토큰이 없는
  주소로 redirect하므로, 토큰이 주소창과 리퍼러에 남지 않는다.
- redirect 목적지: `/newsletter/check-in?goal=<값>&c=<campaign>` (결과 표시 전용, 저장하지 않음)
- 검증에 실패한 링크(만료, 재사용, 잘못된 goal)도 같은 착지 페이지로 보내되 `state=expired` 같은
  구분 값을 붙여 안내만 한다. 저장은 하지 않는다.

### `campaign` 허용값

| 값 | 쓰는 메일 |
|---|---|
| `welcome` | 웰컴 (day0) |
| `day1`, `day3`, `day7` | 온보딩 서베이 |
| `w<ISO주차>` 예: `w2026-34` | 정기호 |

### 온보딩 서베이 질문 계약 (2026-08-17 확정)

온보딩 1, 3, 7일차는 강의형이 아니라 서베이형이다. 링크는 `goal=` 대신 `q=`(질문)과 `a=`(답)를
쓴다. 착지 페이지는 해당 질문의 현재 분포를 바로 보여 준다.

| campaign | q | a 허용값 | 질문 |
|---|---|---|---|
| `day1` | `main-model` | `chatgpt`, `claude`, `gemini`, `other` | 주력 AI 모델 |
| `day3` | `ai-spend` | `free`, `one-paid`, `multi-paid`, `company` | AI 월 지출 형태 |
| `day7` | `ai-level` | `level1`, `level2`, `level3`, `level4` | AI 활용 단계 자가진단 |

정기호의 "이번 주 질문" 코너도 같은 형식을 쓴다. 질문이 늘 때마다 이 표에 추가한다.

**토큰 재사용 판정 변경.** 서베이가 메일마다 있으므로 일회성은 토큰 단독이 아니라
**(token, campaign) 조합 단위**로 판정한다. 같은 토큰이라도 캠페인이 다르면 응답을 받고, 같은
캠페인에서 두 번째 클릭부터는 저장 없이 분포만 보여 준다. `newsletter_checkins`의 유니크 제약을
(subscriber_id, campaign, q)로 잡으면 된다.

### UTM

메일 링크에는 `utm_source=newsletter`, `utm_medium=email`, `utm_campaign=<campaign>`을 함께 붙인다.
GA4 세션 귀속용이고, 체크인 API는 UTM이 아니라 `goal`, `c`, `t`만 읽는다.

### 토큰 규격

| 항목 | 값 |
|---|---|
| 형식 | HMAC-SHA256 서명, base64url 인코딩. 비밀 키는 환경변수 `NEWSLETTER_TOKEN_SECRET` |
| 담는 것 | 구독자 식별자, `purpose=welcome-checkin`, 발급 시각 |
| 만료 | 발급 후 30일. 웰컴 메일을 며칠 뒤에 여는 경우를 허용 |
| 일회성 | Neon `newsletter_tokens`에 해시로 저장하고 `used_at` 기록 후 재사용 거절 |
| 재클릭 | 같은 토큰의 재클릭은 저장 없이 착지 페이지만 보여 준다 (멱등) |

## 4. 결제 후 확인 체크리스트

API 키를 받은 뒤 테스트 구독자 한 명으로 확인하고 결과를 이 표에 채운다.
2026-08-17에 읽기 항목을 확인했다. API 키는 `.env.local`의 `STIBEE_API_KEY`에 둔다.

| # | 확인할 것 | 방법 | 결과 |
|---|---|---|---|
| 1 | API 키 인증 | `GET https://api.stibee.com/v2/auth-check` | **확인 (2026-08-17).** 200 `ok` |
| 2 | API로 구독자 추가 시 구독 확인 메일이 나가는지, 즉시 구독 상태인지 | 구독자 추가 API 호출 후 상태 조회 | **확인 (2026-08-17). 파라미터로 방식을 고른다.** `eventOccuredBy=SUBSCRIBER, confirmEmailYN=Y`면 `ready` 상태로 들어가고 확인 메일이 나간다. `MANUAL, N`이면 즉시 `subscribed`가 된다 |
| 3 | API 추가가 자동 이메일(구독자 추가 트리거)을 발동시키는지 | 자동 이메일 켜고 테스트 추가 | 대기 (자동 이메일 등록 후 재확인) |
| 4 | 사용자 정의 필드가 채워진 채로 추가하면 메일머지에 반영되는지 | `welcome_token` 넣고 수신 메일의 링크 확인 | 절반 확인 (2026-08-17). 추가 요청의 필드는 즉시 저장된다. 메일머지 반영은 3번과 함께 재확인 |
| 5 | 구독자 추가와 필드 채움의 순서 (토큰이 비어 있는 채 발송될 수 있는지) | 추가와 수정을 나눠 호출해 타이밍 확인 | **확인 (2026-08-17). 추가 요청 본문에 필드를 넣으면 한 번에 저장된다.** 같은 이메일 재요청은 `update`로 멱등 처리되고 필드가 갱신된다. 토큰은 추가 요청에 포함해 넣으면 빈 채 발송될 틈이 없다 |
| 6 | 웹훅 수신 (구독, 수신거부) | 주소록 웹훅에 테스트 URL 등록 후 이벤트 발생 | 대기 (라우트 구현 후) |
| 7 | 이메일 주소로 구독자 1명을 조회하는 엔드포인트 | API 문서 대조 후 호출 | **확인 (2026-08-17). 전용 엔드포인트 없음.** v1, v2 모두 path 조회 404. 목록 조회로 대체한다 (아래) |

### 확인된 실측 정보 (2026-08-17)

| 항목 | 값 |
|---|---|
| 주소록 | `준이아빠블로그 구독자`, **id 508786** (2026-08-04 생성) |
| 구독자 | 14명, 전원 `subscribed`. 2026-08-06부터 거의 매일 1~3명씩 유입 중 |
| 기존 필드 | `name`, `$ad_agreed` (둘 다 값이 비어 있는 구독자가 많음) |
| 만들 필드 | `goal`, `signup_source`, `welcome_token` (스티비 화면에서 생성. API 필드 생성 경로는 404) |
| 목록 조회 | `GET /v2/lists/508786/subscribers?offset=&limit=` 200. 응답에 `fields`, `status`, `groupIds` 포함 |
| 단건 조회 대체 | 게이트 조회의 원본은 Neon 원장이고 스티비는 웹훅으로 동기화하므로 단건 API가 없어도 구조에 영향 없음. 필요 시 목록 조회(분당 100회 제한)로 확인 |
| v1 API | `GET /v1/lists` 200 (주소록 목록). v1 구독자 목록도 200이지만 v2와 응답 형식이 다름. 조회는 v2, 추가/삭제는 v1을 쓴다 |
| 필드 미생성 시 동작 | **스티비에 없는 커스텀 필드를 추가 요청에 넣으면 오류 없이 무시된다** (2026-08-17 실측). 화면에서 필드를 만들기 전 가입자는 이메일만 저장되므로, 필드 6개 생성을 서두른다 |

2번 결과가 "확인 메일이 나간다"이면 더블 옵트인 흐름을 그대로 쓰고, "즉시 구독"이면 자체 폼의
동의 체크가 유일한 동의 증빙이 되므로 Neon 기록을 반드시 남긴다.

5번이 "추가 즉시 발송"으로 나오면, 토큰을 먼저 만들어 **추가 요청에 필드를 포함**해 한 번에
넣는다. 추가 후 수정 방식은 빈 토큰으로 발송될 위험이 있다.

## 5. 스티비에 손으로 설정할 것 (결제 직후)

1. 워크스페이스 설정 > API 키 > 새로 만들기 (2025-01-21 이후 생성 키만 인증된다)
2. 주소록에 사용자 정의 필드 6개 생성: `goal`, `signup_source`, `welcome_token`, `industry`, `job_role`, `years`
3. 자동 이메일: 트리거 구독자 추가, 즉시 발송, 콘텐츠는 `day0-welcome.html`
4. 주소록 > 웹훅: URL `https://www.digitalmarketer.co.kr/api/stibee/webhook`,
   이벤트 전부 선택 (구독, 정보변경, 수신거부, 수신거부 취소, 자동삭제, 완전삭제).
   발신 IP는 52.78.132.66이고 실패 시 3회 재시도된다. 라우트 구현 전에는 등록하지 않는다
